# 齐齐哈尔粮食商情企业平台正式架构设计

> 日期：2026-07-31
>
> 状态：待用户最终确认
>
> 定位：中粮企业内部经营决策与区域研判平台
>
> 约束：内部可以发布正式经营版本，但不得冒充政府官方统计结果

## 一、设计结论

不继续修补当前简化版，也不恢复旧版，而是建立第三套正式架构：

- 保留旧版有效的信息密度、业务层级和操作台感；
- 保留新版已经建立的领域边界、类型约束和前后端分离方向；
- 删除两版中的演示菜单、重复入口、万能页面、前端正式计算和技术信息泄露；
- 以角色任务、业务对象、规范事实、审核发布和决策结果重新组织系统；
- 以自动测试、架构扫描、安全门禁、可恢复性和阶段验收证明成熟度。

“成熟、先进、稳定”不是视觉形容词，而是以下能力同时成立：

1. 同一对象只有一个身份；
2. 同一现实事件只有一个规范事实；
3. 同一数量只有一个事实所有者；
4. 不同生命周期、责任人、频率和审核链保持独立；
5. 共用质量、审核、发布和权限能力只建设一次；
6. 正式计算、权限判断、导出和发布由后端权威执行；
7. 所有正式结果可追溯、可重述、可恢复且历史不可覆盖；
8. 页面只呈现已实现、已授权且有明确业务用途的能力。

## 二、范围与非目标

### 2.1 平台服务对象

平台服务于三类角色：

- 业务执行人员：填报、采集、修正、审核和发布；
- 部门管理人员：履责、质量、异常、风险和资源协调；
- 决策分析人员：供需账户、经营态势、区域比较和正式报告。

不同角色获得不同工作空间。系统不为所有人显示同一套全菜单。

### 2.2 平台不承担

- 不作为政府官方统计发布平台；
- 不把调查样本直接描述为区域总体；
- 不以报表反向写入业务事实；
- 不把报价、合同、交付、物流和结算合并成万能交易记录；
- 不把企业库存、政策库存、原料库存和成品库存当作同级数量相加；
- 不在前端保存正式供需公式或决定正式发布；
- 不为了视觉完整而展示尚未实现的功能。

## 三、总体业务架构

```text
控制与治理层
  组织、账号、岗位、任职、责任、权限、主数据、表单、指标、质量规则
            ↓
业务作业层
  我的工作、产情监测、市场监测、单据、质量、审核、发布
            ↓
规范事实与指标层
  原始主张、匹配去重、规范事实、事实发布、指标发布
            ↓
决策与报告层
  供需账户、账户勾稽、经营态势、区域地图、正式报告
```

数据只能沿上述方向流动。决策页面和报告不得成为业务事实来源。

### 3.1 四个一级工作空间

1. **我的工作**
   - 待填报；
   - 待审核；
   - 异常与逾期；
   - 待发布；
   - 已办跟踪。

2. **业务运营**
   - 产情运营；
   - 市场运营。

3. **决策分析**
   - 供需决策；
   - 经营态势；
   - 区域地图；
   - 正式报告。

4. **治理与管理**
   - 组织、人员和岗位；
   - 责任和权限；
   - 主数据；
   - 表单、指标和公式；
   - 质量规则与审核流程；
   - 版本、血缘、审计和安全。

一级入口按能力投影。未实现或无权限的入口不渲染。

## 四、同类业务合并与异类业务分离原则

### 4.1 保持独立的判断

满足任意一项就保持独立：

- 生命周期不同；
- 报送频率不同；
- 责任岗位不同；
- 审核链不同；
- 更正、撤销或重述规则不同；
- 权威数量来源不同。

### 4.2 允许组合展示的判断

以下条件同时成立时可在一个工作区组合展示：

- 围绕同一业务目标；
- 面向同一对象或产品账户；
- 用户需要在一次任务中共同查看；
- 后台事实仍保持各自类型、所有权和生命周期。

对象全景和产品账户是查询组合，不是万能数据库表或万能单据。

### 4.3 必须消除的重复

- 农户销售数量与农户库存销售变动重复；
- 农户销售主张与企业采购主张未经匹配形成两份规范交易；
- “我的工作”和各模块分别保存第二套任务状态；
- 各模块重复建设质量、审核、发布和版本实体；
- 同一主体在样本、市场企业和设施页面重复建档；
- 同一供需结果在总览、账户、勾稽和报告中分别计算。

## 五、产情监测正式架构

### 5.1 业务边界

产情监测包括：

- 监测方案、抽样框、样本成员和权重；
- 行政村台账、农技站观察和农户样本；
- 农业经营主体、农户、受访人、地块和作物季；
- 生育进程、墒情、灾害、病虫害、测产和收获进度；
- 播种面积、收获面积、弃收面积、单产和产量；
- 成本、补贴、保险、赔付和灾害损失；
- 农户库存快照、库存变动和销售；
- 下一年度种植意愿；
- 区域估计、质量、审核和正式发布。

如正式建设不包含全年田间监测能力，模块必须改名为“种植生产调查”，不得以超出能力的名称对外展示。

### 5.2 五个工作区

1. **产情总览**
   - 采集覆盖；
   - 履责进度；
   - 质量风险；
   - 正式产量与历史比较；
   - 当前灾情和收获态势。

2. **种植生产**
   - 地块和作物季；
   - 面积、长势、灾害、测产、单产和产量；
   - 成本、补贴和保险作为对象内“生产经济”页签。

3. **农户库存与销售**
   - 库存快照；
   - 收获入库、消费、销售、损耗、代存和批准调整；
   - 销售数量只由库存变动拥有；
   - 销售详情仅扩展价格、买方和交付信息。

4. **种植意愿**
   - 下一作物年度；
   - 预计面积；
   - 变化原因；
   - 可用耕地约束；
   - 只进入预测和研判，不进入本期正式供需。

5. **质量与发布**
   - 多来源比较；
   - 覆盖率和置信区间；
   - 冲突和异常；
   - 分级审核；
   - 事实与指标发布。

### 5.3 三类来源

行政村台账、农技站专业观察和农户样本不直接相加。正式指标必须绑定版本化采用策略：

- 直接采用某一来源；
- 某一来源为基准、其他来源校准；
- 样本加权估计；
- 经批准的多源联合估计。

未配置采用策略时只能并列展示，不能发布区域总量。

## 六、市场监测正式架构

### 6.1 业务边界

市场监测包括：

- 经营主体、经营场所、设施、物流节点和有效关系；
- 业务角色、能力和能力模板；
- 产品、品种、质量、包装、交付和计价条件；
- 报价；
- 交易协议、交易行、交付和结算；
- 粮食批次、质量检验和批次血缘；
- 物理库存、所有权、保管和库存属性；
- 加工投入、产出、副产品、损耗和直接消费；
- 运输任务、运输分段和统计边界穿越；
- 政策授权、政策账户和政策执行事件；
- 样本估计、质量、审核和正式发布。

### 6.2 六个工作区

1. **市场总览**
   - 价格态势；
   - 成交与交付；
   - 库存覆盖；
   - 加工开工与投料；
   - 区域流向；
   - 质量和履责风险。

2. **市场主体与设施**
   - 同一企业只建立一份主体档案；
   - 角色、能力、场所、设施、所有、经营、租赁和保管关系分别管理。

3. **行情与交易**
   - 报价、交易协议、交付和结算在同一工作区组合查看；
   - 四者保持独立事实、状态和责任边界；
   - 报价不等于成交；
   - 合同数量在交付前不进入实物供需。

4. **库存与仓储**
   - 唯一物理持仓；
   - 所有权份额；
   - 保管责任；
   - 政策、商业、原料、在制和成品等正交属性；
   - 盘点、流水、调查和批准调整分别保存。

5. **加工与消费**
   - 原料投入；
   - 主产品和副产品产出；
   - 损耗和在制品变化；
   - 直接食用、饲用、种用和其他直接消费；
   - 上下游产品账户通过同一加工运行成对记账。

6. **物流与区域流向**
   - 运输任务；
   - 铁路或公路分段；
   - 装卸和到货；
   - 唯一统计边界穿越；
   - 区域流入、流出只由边界穿越产生。

农业投入品行情第一阶段不进入粮食市场主链。后续如有真实用户、来源、频率和决策用途，再建立独立能力。

## 七、供需决策正式架构

### 7.1 四个工作区

1. **供需总览**
   - 按产品、区域、年度和版本展示正式结果；
   - 明确正式、初步、暂估和预测状态。

2. **产品账户**
   - 玉米原粮；
   - 原豆、豆粕、豆油和蛋白产品；
   - 稻谷和大米；
   - 不同产品形态不得直接相加。

3. **账户勾稽**
   - 总供给；
   - 期间总使用与外流；
   - 调整前账面推算期末库存；
   - 已批准库存调整；
   - 采用后账面期末库存；
   - 调查汇总期末库存；
   - 库存平衡差额。

4. **版本与血缘**
   - 输入指标版本；
   - 账户规范；
   - 库存合并矩阵；
   - 公式与转换版本；
   - 计算运行；
   - 结果版本；
   - 上游重述和下游待重算。

实时监控和区域地图属于决策分析空间，不属于供需账户内部菜单。

### 7.2 权威数据流

```text
原始单据和外部来源
→ 原始主张
→ 匹配、去重和冲突处置
→ 规范事实
→ 事实发布版本
→ 指标发布版本
→ 指标到账户角色的唯一映射
→ 后端供需计算
→ 供需结果发布版本
→ 报告、态势和地图
```

前端不能保存正式供需公式、补零、批准调整或决定发布。

### 7.3 产情、市场与供需映射

| 上游事实或指标       | 供需用途                           |
| -------------------- | ---------------------------------- |
| 正式产量指标         | 本地产量                           |
| 农户和企业正式库存   | 经库存合并矩阵去重后的库存构成     |
| 农户销售与企业采购   | 交易来源证据，不直接增加区域总供给 |
| 市场报价             | 价格指标，不进入实物数量           |
| 实际加工投料         | 上游产品账户的加工使用             |
| 加工产出             | 下游产品账户的本地生产             |
| 直接食用、饲用和种用 | 对应互斥使用角色                   |
| 统计区域边界穿越     | 区域流入或流出                     |
| 政策收购、投放和轮换 | 政策账户；不自动增加区域实物总量   |
| 种植意愿             | 下一年度预测，不进入本期正式账户   |
| 成本、补贴和保险     | 经营效益分析，不进入实物供需账户   |

## 八、页面与视觉架构

### 8.1 三种页面原型

不同业务不再共用万能页面。

#### 业务操作工作台

适用于产情、市场的填报、采集、审核和异常处置：

- 页级业务动作；
- 当前组织、责任区域、产品、期间和截止时点；
- 生命周期；
- 待处理异常；
- 对象或任务清单；
- 对象全景抽屉；
- 质量、审核、来源和历史页签。

#### 决策工作台

适用于供需、态势和区域研判：

- 产品、区域、年度和版本选择；
- 标准账户或指标主体；
- 勾稽关系和差额；
- 数据资格和截止时点；
- 单元格血缘；
- 历史版本比较；
- 不提供未经授权的填报操作。

#### 管理驾驶舱

适用于管理者：

- 履责、质量、逾期和风险；
- 各区域或组织比较；
- 已发布正式结果；
- 需要管理决策的问题；
- 不直接复制业务人员的明细填报页面。

### 8.2 视觉方向

视觉定位为“高密度、低噪声、强业务秩序的企业运营控制台”。

#### 色彩

- 粮政深蓝 `#0B2A3B`：全局壳层和权威上下文；
- 治理青绿 `#167C74`：当前业务、主操作和已确认状态；
- 业务画布 `#F3F6F8`：内容背景；
- 数据纸白 `#FFFFFF`：表格、账户和单据；
- 结构分隔 `#D6E0E6`：层级和边界；
- 风险琥珀 `#B88318`：待处理、暂估和风险。

红色只用于阻断、安全和不可继续状态，不作为装饰色。

#### 字体

- 页面标题：本地可用的思源黑体或苹方中黑；
- 正文与表格：苹方、微软雅黑或等价中文无衬线体；
- 数字：使用等宽数字特性，保证账户列与时间列可比较。

不得依赖外部字体网络请求。

#### 布局

- 桌面端以 `1440×900` 为主要业务验收尺寸；
- 全局导航和业务上下文最多两层；
- 核心任务、主要异常和主业务对象在首屏可见；
- 不使用巨型留白、无业务含义的大卡片和装饰性渐变；
- 表格、账户和时间轴承担主要信息组织；
- 移动端聚焦查阅、审批和异常处理，不强行复制桌面宽表。

#### 识别性元素

每个工作台使用一条“责任与版本轨道”，连续呈现：

```text
责任组织 → 当前岗位 → 业务期间 → 数据截止 → 质量资格 → 审核状态 → 发布版本
```

它是业务控制信息，不是装饰。

### 8.3 全中文与技术隔离

普通业务界面不得显示：

- 英文技术词；
- API 路径；
- JSON、数据库或框架术语；
- 内部枚举和异常堆栈；
- 原始技术标识；
- “演示页面”“开发中”“兼容测试”等开发状态。

源代码仍使用规范的 TypeScript、Java、OpenAPI 和英文标识。强行把源代码中文化不属于成熟工程。

必要技术详情只进入受限运维入口，并提供中文说明和关联号。

## 九、前后端与数据架构

### 9.1 前端

```text
app：应用装配、全局提供器和路由
pages：页面组合，不拥有业务规则
workflows：业务用例、查询和视图状态
domains：领域类型、不变量和纯规则
platform：HTTP、模拟和浏览器适配器
shared/enterprise-ui：无业务所有权的企业界面组件
```

约束：

- 页面不得反向依赖应用装配；
- 工作流和领域不得依赖 Refine、Ant Design 或 HTTP 类型；
- 模拟适配器和 HTTP 适配器实现同一网关端口；
- 正式构建不得固定注入模拟网关；
- 模块工作区不得直接读取静态业务目录；
- 共用组件不得保存产情、市场或供需业务规则。

### 9.2 后端

采用独立 Java/Spring Boot 模块化单体，按稳定业务域分模块：

- 基础与主数据；
- 身份、组织与责任；
- 报送与单据；
- 产情监测；
- 市场监测；
- 质量、审核与发布；
- 指标与供需账户；
- 报告与态势；
- 审计与运行保障；
- HTTP、安全和配置适配器。

跨模块只调用公开接口或消费正式事件。不得访问其他模块内部类或直接读写其他模块的数据表。

### 9.3 前后端边界

- 独立仓库；
- 独立构建；
- 独立测试；
- 独立进程和端口；
- 独立发布制品；
- 只通过版本化 OpenAPI/HTTP 通信；
- 前端不接数据库；
- 后端不包含 React 页面或浏览器状态。

### 9.4 数据库

新数据库只在物理模型、迁移、恢复和安全门禁通过后创建。不得在旧库直接改造成新模型。

正式数据库必须以唯一约束、外键、版本字段、幂等键和不可变发布结构兜底：

- 唯一责任人；
- 唯一规范事实；
- 唯一当前正式版本；
- 同一批次份额的唯一物理位置；
- 指标到账户角色的唯一映射；
- 同一坐标的并发发布互斥。

## 十、安全、稳定与恢复

### 10.1 权限

权限判断至少包含：

- 用户与有效任职；
- 责任区域；
- 业务应用；
- 对象与字段敏感级别；
- 当前业务状态；
- 操作；
- 时间；
- 环境。

必须先鉴权和确定数据范围，再读取业务数据。导出需要重新鉴权、字段脱敏、数量限制和审计。

### 10.2 一致性

- 提交、审计和发件箱在同一事务；
- 相同幂等键只产生一个结果；
- 并发领取、责任交接和发布不能产生双负责人或双正式版本；
- 上游重述只生成新版本，并标记下游待重算；
- 后台任务具备租约、重试、失败终态和人工处置。

### 10.3 可恢复性

- 加密备份和保留策略；
- 隔离恢复演练；
- 恢复后重算数量、哈希和关键勾稽；
- 回退条件、恢复点目标和恢复时间目标；
- 发布前保存可验证准入证据；
- 未演练的能力不得声明为已经达到。

### 10.4 可观测性

- 结构化日志；
- 关联号；
- 健康、依赖和任务积压指标；
- 权限拒绝、导出、发布、重述和恢复审计；
- 不记录凭据、会话、敏感字段或完整请求正文。

## 十一、验收门禁

### 11.1 业务门禁

- 同一业务无重复事实源；
- 不同业务无万能单据；
- 正式数量能够指出唯一所有者；
- 产情、市场到供需的每个映射可解释且互斥；
- 样本数据不冒充总体；
- 初步、暂估、预测和正式结果清晰分层。

### 11.2 工程门禁

- 格式、静态检查、类型检查、架构依赖扫描全部通过；
- 单元、契约、集成、并发、恢复和端到端测试通过；
- 前后端可分别启动、停止、构建和定位故障；
- 正式构建不包含模拟业务事实；
- 供需公式不在浏览器；
- 端到端测试只访问现行正式路由。

### 11.3 视觉与可用性门禁

- 普通业务界面全中文；
- 每个常驻入口都有用户、任务、权限和真实结果；
- 核心任务在首屏可发现；
- 同一动作全程使用同一名称；
- 空状态和错误状态说明下一步；
- 键盘焦点、对比度和缩放可用；
- `1440×900`、宽屏和移动审批场景分别验收；
- 不以空卡片、假指标或无效按钮制造“大系统”外观。

### 11.4 性能门禁

- 初始包体、最大分包和预加载体积设硬预算；
- 大表格使用服务端分页、筛选和受控导出；
- 指标计算和供需计算在后台异步运行；
- 页面不得一次加载无权限或不可见的完整数据；
- 性能预算失败时不得以提高上限代替拆包和按需加载。

## 十二、实施顺序

### 阶段 0：冻结与收口

- 保留当前工作区证据；
- 隐藏演示和未实现菜单；
- 停止继续扩展万能页面和静态业务目录；
- 固化新旧页面对比基线。
- 在不连接数据库、不冒充正式功能的独立视觉样板中，制作“我的工作、产情监测、市场监测、供需平衡”四个代表页面；
- 样板必须展示真实的信息层级、角色上下文、业务动作、异常、生命周期、表格或账户关系，不使用空卡片和假功能凑页面；
- 用户确认视觉架构、信息密度、中文业务语言和主要交互后，才允许进入正式前端实现。

### 阶段 1：正规工程基础

- 完成独立前端壳层、角色工作空间和架构门禁；
- 创建独立 Java/Spring Boot 无数据库后端；
- 建立 OpenAPI、身份、责任、权限、审计和运行基线；
- 不连接旧数据库。

### 阶段 2：共用治理纵向链

- 我的工作；
- 报送义务；
- 规范单据；
- 原始主张；
- 质量、审核、发布；
- 对象全景；
- 前后端真实契约。

### 阶段 3：产情监测

- 先完成种植生产纵向链；
- 再完成农户库存与销售；
- 再完成种植意愿；
- 最后完成多源采用、区域估计和正式发布。

### 阶段 4：市场监测

- 主体与设施；
- 报价、交易、交付和结算；
- 库存与仓储；
- 加工与消费；
- 物流与区域流向；
- 跨来源匹配和正式发布。

### 阶段 5：指标与供需

- 指标定义和发布；
- 产品账户规范；
- 账户角色唯一映射；
- 后端计算和勾稽；
- 结果发布、血缘和重述；
- 预测情景与正式结果分离。

### 阶段 6：决策与报告

- 经营态势；
- 区域地图；
- 履责报告；
- 业务分析报告；
- 历史版本比较。

每个阶段只展示已经实现并通过验收的能力。不得为完整菜单提前创建占位页面。

## 十三、完成定义

只有同时满足以下条件，才能称为本阶段完成：

1. 实际源码符合前后端正规分层；
2. 业务事实所有权和跨域关系通过独立审查；
3. 全部自动门禁通过；
4. 浏览器逐页视觉和交互验收通过；
5. 安全、并发、恢复和可观测性有对应证据；
6. 用户能够完成真实业务任务，而不是只看到演示数据；
7. 未完成项被隐藏并明确记录，不以页面数量冒充系统成熟度。
8. 正式页面与用户批准的高保真视觉样板保持同一信息架构；若实现中必须偏离，先记录原因并重新确认。
