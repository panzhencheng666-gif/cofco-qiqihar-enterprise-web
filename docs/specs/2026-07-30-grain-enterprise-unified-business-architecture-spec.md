# 齐齐哈尔粮食商情企业平台统一业务架构规格

> 日期：2026-07-30
>
> 状态：候选冻结版，待业务、统计、审计和技术联合评审
>
> 适用范围：新 React 企业平台、后端领域重构、新数据库模型、旧数据迁移与正式发布验收
>
> 约束：本规格不授权直接删除旧系统、旧数据库或历史证据

## 一、问题陈述

现有系统和早期重构设计存在以下核心问题：

1. 业务按照企业类型、品种、报表和页面不断拆分，同一主体和同一事实容易在多个位置重复维护。
2. 为了避免拆散业务，又存在把收购、库存、加工、销售和物流强行塞入一份万能单据的风险。
3. 行政区域、组织、人员、农户、企业、设施、地点、业务角色和证据来源尚未形成严格边界。
4. 现有“用户—区域”权限只能表达可查看或可编辑，不能证明同一报送事项只有一个有效负责人。
5. 请假、离职、责任变更、未完成任务转移、逾期归责和补填执行人缺少完整规则。
6. 报送时效、单据流程、数据质量和发布状态被混为一个状态，无法准确形成履责记录。
7. 产情存在累计销售、销售事件、期初结转、重新填报期初和种植意愿重复填写当前面积等竞争事实。
8. 市场业务尚未严格区分报价、交易、批次、质量检验、库存、加工和物流。
9. 样本数据缺少完整抽样设计、覆盖率、权重和不确定性，不能直接代表区域总量。
10. 玉米、大豆、稻谷和大米供需账户仍存在重复计算、产品混算、流量重复和缺失值补零风险。
11. 日报、周报和月报尚未形成固定数据版本、生成运行、人工复核、审批发布和修订替代链路。
12. 当前新前端主要是技术兼容和只读骨架，不能以页面原型证明企业级业务能力已经完成。
13. 用户界面仍可能暴露开发占位、技术门禁、英文缩写、内部状态码或原始错误。
14. 旧数据库口径与新版业务口径不同，直接删除或直接复用都会造成不可逆的数据损失或语义污染。

用户需要的不是一套继续堆菜单的报表系统，也不是一个难以维护的万能表单平台，而是一套：

- 业务聚合但事实不混乱；
- 权限精确且责任唯一；
- 报送、审核、发布和报告完整闭环；
- 供需自动计算且不重复；
- 可追溯、可重现、可修订、可恢复；
- 全中文、清晰、稳定、适合大型企业长期演进的粮食商情企业平台。

## 二、解决方案

### 2.1 唯一推荐方案

采用：

```text
统一工作入口
＋类型化领域对象与业务事实
＋对象全景档案投影
＋责任岗位和报送义务引擎
＋质量、审核和不可变发布
＋规范指标与供需账户
＋正式报告中心
＋模块化单体后端
```

不采用：

- 按企业类型、品种和报表复制页面与数据库表；
- 万能对象、万能字段、万能单据或万能宽表写模型；
- 浏览器直接连接数据库；
- 前端承担服务端权限、审核状态机、供需公式或正式发布；
- 当前阶段全面微服务化；
- 所有状态都依赖事件重放的全事件溯源架构；
- 未完成口径确认就直接建立正式数据库；
- 新口径未完成映射和验收就删除旧数据库。

### 2.2 三层统一企业架构

#### 控制与治理层

负责：

- 组织、人员、账号、角色；
- 责任岗位、有效任职和责任范围；
- 报送计划、业务日历和每期报送义务；
- 行政区划、统计区域和有效期；
- 监测方案、样本框和样本成员；
- 指标、单位、产品、表单、质量规则和公式；
- 权限、职责分离、隐私和审计；
- 版本、生效、停用、替代和历史查询。

#### 业务作业层

负责：

- 我的工作；
- 产情监测；
- 市场监测；
- 政策授权台账；
- 单据填报、批量录入和文件导入；
- 质量校验、退回、更正、审核和发布；
- 对象全景档案；
- 任务、通知、催办和异常处置。

#### 决策与报告层

负责：

- 事实发布版本；
- 规范指标和区域估计；
- 供需平衡与账户勾稽；
- 实时监控与区域地图；
- 履责日报、周报和月报；
- 业务分析日报、周报和月报；
- 版本对比、来源下钻和审计追溯。

### 2.3 权威数据流

```text
组织与责任配置
→ 报送计划
→ 当期报送义务
→ 单据修订
→ 不可变原始主张
→ 主张质量门禁与提交审核
→ 候选匹配、冲突和重复处置
→ 类型明确的规范事实
→ 规范事实质量门禁与发布审核
→ 事实发布版本
→ 规范指标
→ 指标发布版本
→ 供需计算运行
→ 供需结果发布版本
→ 态势与报告运行
→ 报告发布版本
```

任一后续层不得静默改写前一层事实。

报告、看板和供需页面不得成为新的业务事实写入口。

## 三、统一业务语言

以下术语在系统中只能有一个含义：

| 术语             | 唯一含义                                                           |
| ---------------- | ------------------------------------------------------------------ |
| 账号             | 用于登录和鉴权的技术身份，不等同于员工本人                         |
| 人员             | 组织中的自然人身份，停用账号不删除人员历史                         |
| 责任岗位         | 对某类报送事项承担持续责任的业务岗位                               |
| 有效任职         | 某人员在明确生效期内担任某责任岗位的关系                           |
| 责任范围         | 组织、业务域、报送事项、地区、对象、产品和有效期共同限定的写入范围 |
| 报送计划         | 定义报送内容、频率、日历、截止时间、表单和审核链的版本化规则       |
| 报送义务         | 根据报送计划为某一期间生成的一次应报责任                           |
| 业务单据         | 在同一责任人、报告期间、审核边界和表单版本下的一次完整填报载体     |
| 业务事实         | 可追溯的观察、状态快照、业务事件或批准调整                         |
| 对象全景档案     | 聚合展示同一对象相关业务的查询与协作投影，不是万能数据表           |
| 经营主体         | 承担法律、合同或经营责任的组织                                     |
| 设施             | 仓库、工厂、生产线、经营场所等物理资源                             |
| 物流节点         | 铁路站点、公路节点等运输网络地点                                   |
| 样本主体         | 纳入监测方案的农业经营主体、农户、组织或设施                       |
| 粮食批次         | 具有稳定产品、来源和质量身份的一批粮食                             |
| 事实发布版本     | 通过质量和审核门禁、固定且不可覆盖的规范事实集合                   |
| 指标发布版本     | 使用固定事实版本、定义和聚合规则生成的不可变指标集合               |
| 供需结果发布版本 | 使用固定指标版本、账户规范和公式生成的不可变供需结果               |
| 报告发布版本     | 引用固定版本清单、经复核审批并固定文件哈希的正式报告               |
| 计算运行         | 使用固定输入、公式、参数和代码版本执行的一次可重现计算             |
| 履责快照         | 在固定截止时点保存的应报、按时、逾期、补填和未填状态               |
| 报告运行         | 使用固定数据截止时点、正式版本和模板生成报告的一次运行             |

必须区分：

- 行政区域、统计区域和业务管理区域；
- 行政村与自然村；
- 行政村、村委会和村级台账；
- 人员、账号和责任岗位；
- 经营主体、经营场所、设施和物流节点；
- 业务角色、业务能力和库存政策属性；
- 作物、原粮商品、具体品种、产品形态和质量规格；
- 作物年度、营销年度、报告期间、业务日期、观测时点和系统记录时间；
- 报送时效、单据流程、数据质量和发布状态；
- 测量事实、估计事实、派生指标、构成明细、校验项、预测项和批准调整。

## 四、用户故事

1. 作为填报人员，我希望只看到自己当前有效责任范围内的任务，以便快速完成工作。
2. 作为填报人员，我希望只有自己能够修改专属责任范围的数据，以防他人代填或篡改。
3. 作为填报人员，我希望清楚看到开放时间、截止时间和剩余时间，以免错过报送。
4. 作为填报人员，我希望系统自动保存草稿但只在明确提交后计入履责，以免误提交。
5. 作为填报人员，我希望提交前看到阻断性错误和警告，以便一次完成正确填报。
6. 作为填报人员，我希望被退回时看到具体字段、原因和整改要求，以便准确修正。
7. 作为填报人员，我希望补填时保留原逾期状态和补填时间，以保证记录真实。
8. 作为填报人员，我希望在责任正式转移后无法继续修改该范围数据，以防责任混乱。
9. 作为新负责人，我希望收到正式转移给我的未完成任务，并知道此前责任和草稿来源。
10. 作为审核人员，我希望只审核自己授权区域和业务范围的数据，以防越权。
11. 作为审核人员，我希望不能直接修改填报值，只能退回并说明原因，以保持责任清晰。
12. 作为发布人员，我希望只能发布已通过质量和分级审核的数据，以保护正式结果。
13. 作为发布人员，我希望不能发布自己提交的数据，以满足职责分离。
14. 作为管理人员，我希望看到团队应报、按时、逾期补填和仍未填报情况，以便履责管理。
15. 作为管理人员，我希望履责记录按截止时点冻结，后续补填不能改写历史。
16. 作为管理人员，我希望区分报送及时性、有效数据覆盖率、审核完成率和质量问题，而不是只看一个完成率。
17. 作为系统管理员，我希望配置责任岗位和人员任职关系，但不能代替业务人员填写数据。
18. 作为系统管理员，我希望责任转移经过审批并保留原因、生效时间和影响任务。
19. 作为安全管理员，我希望所有查询、搜索、统计、导出和报告都遵守相同数据权限。
20. 作为安全管理员，我希望权限变更后相关会话、缓存和后台任务及时失效。
21. 作为产情填报人员，我希望在同一产情档案查看种植生产、成本保障、库存销售和种植意愿。
22. 作为产情填报人员，我希望不同频率、不同审核边界的数据形成不同单据，避免互相阻塞。
23. 作为产情分析人员，我希望行政台账、农技站观察和农户样本并列比较，而不是直接相加。
24. 作为产情分析人员，我希望知道区域估计的样本范围、覆盖率、权重和不确定性。
25. 作为产情分析人员，我希望面积按耕地实际所在地统计，而不是只按农户居住地。
26. 作为产情分析人员，我希望播种面积、收获面积和灾损面积明确区分。
27. 作为成本分析人员，我希望分别查看生产经济成本、现金投入、政策支持、保险赔付和净现金负担。
28. 作为成本分析人员，我希望每项成本按正确适用面积分摊，避免统一除以错误面积。
29. 作为农户库存分析人员，我希望库存快照和销售、自用、损耗事件自动勾稽。
30. 作为农户销售分析人员，我希望累计销售量由有效销售事件生成，不重复填写。
31. 作为种植意愿分析人员，我希望引用当前正式面积并填写下一年度意向，避免重复事实。
32. 作为市场填报人员，我希望一个企业只建一份主体档案，即使它同时从事贸易、仓储和加工。
33. 作为市场填报人员，我希望在同一企业或设施工作区完成适用业务，而不在多套菜单重复找企业。
34. 作为企业管理员，我希望区分企业所有、经营、租赁和代储的设施，以正确表达责任。
35. 作为贸易业务人员，我希望报价和实际成交分开记录，以免报价被误计为交易。
36. 作为质检人员，我希望质量检验关联样品、批次、标准和方法，以保证结果可追溯。
37. 作为库存人员，我希望库存记录所有者、保管方、物理地点、库存性质、产品形态和时点。
38. 作为加工人员，我希望记录原料投入、主要产出、副产品、损耗、生产线和报告期间。
39. 作为物流人员，我希望一票运输支持多个运输分段并明确起点、终点和边界穿越。
40. 作为市场分析人员，我希望同一运输的多方报送只形成一个规范物流事实。
41. 作为政策业务人员，我希望政策库存和内部转移单独分账，不重复增加区域供需总量。
42. 作为供需分析人员，我希望供需结果只读取已审核发布的规范指标。
43. 作为供需分析人员，我希望任何缺失值都不会被伪装成真实零。
44. 作为供需分析人员，我希望玉米、大豆、稻谷和大米使用明确、互斥的产品账户。
45. 作为供需分析人员，我希望看到调整前账面推算期末库存、采用后账面期末库存、调查汇总期末库存和库存平衡差额。
46. 作为供需分析人员，我希望点击任一指标可以追溯公式、输入、转换、质量和审核版本。
47. 作为决策人员，我希望默认页面先回答供给从哪里来、使用到哪里去、库存为何变化。
48. 作为决策人员，我希望价格、质量、成本和意愿用于解释，不被错误相加进供需数量。
49. 作为报告编制人员，我希望选择业务、地区、产品、期间和正式版本生成日报、周报或月报。
50. 作为报告编制人员，我希望报告数字与正式指标完全一致，不能由文字生成过程重新计算。
51. 作为报告编制人员，我希望系统生成正式自然中文初稿，但不能编造原因、主体或数字。
52. 作为报告审核人员，我希望在发布前核验事实、语言、数据截止时间和来源。
53. 作为报告使用人员，我希望报告显示版本、截止时间、覆盖率和修订关系。
54. 作为报告使用人员，我希望历史报告不因后续补填或源数据修订而变化。
55. 作为普通业务用户，我希望界面只显示中文业务语言，不出现技术状态码、接口地址或开发占位。
56. 作为普通业务用户，我希望菜单只展示有权限且已具备真实能力的功能。
57. 作为运维人员，我希望技术诊断信息与普通业务界面隔离，以便排障但不干扰用户。
58. 作为审计人员，我希望任何填报、转移、退回、审核、发布、导出和报告下载都可追溯。
59. 作为审计人员，我希望旧版本永不被覆盖或删除，并可证明后续版本替代关系。
60. 作为项目负责人，我希望新旧系统可并行验证并可回退，避免一次性切换失败。

## 五、实施决策

### 5.1 最终导航

正式一级导航固定为：

```text
我的工作
经营总览
产情监测
市场监测
供需与态势
报表中心
数据治理
系统管理
```

规则：

- 导航按角色、责任范围和真实能力投影。
- 不显示无权限、未接入或纯开发测试功能。
- “我的工作”是个人填报、审核、发布、异常和逾期任务的唯一入口。
- 业务模块可以显示筛选后的相关任务，但不得维护另一套任务事实。
- 审核管理作为“我的工作”的授权工作区，不复制业务表单。
- 供需平衡、实时监控和区域地图共享指标定义、业务坐标和血缘；供需只使用正式指标版本，实时监控和地图可以明确区分初步数据层与正式数据层。
- 报表中心统一管理履责报告和业务分析报告。
- 技术兼容、组件试验和调试页面不得进入生产菜单。

一级导航是工作入口，不等于后台重复建库。业务归属固定如下：

| 入口       | 唯一职责                                                     | 不得拥有                         |
| ---------- | ------------------------------------------------------------ | -------------------------------- |
| 我的工作   | 汇总本人填报、审核、发布、异常和逾期任务，并调用对应领域动作 | 第二套任务、单据或业务事实       |
| 经营总览   | 展示已授权的正式指标、风险和任务摘要                         | 手工维护经营数字                 |
| 产情监测   | 维护产情领域单据、主张和事实                                 | 市场交易、企业加工或正式供需结果 |
| 市场监测   | 维护市场、库存、加工、物流和政策执行领域单据、主张和事实     | 农户种植生产事实或手填供需结果   |
| 供需与态势 | 读取发布指标，运行并展示产品账户、态势和血缘                 | 原始业务事实写入口               |
| 报表中心   | 编排、复核、发布和留存报告                                   | 另一套指标或供需计算             |
| 数据治理   | 管理主数据、指标、质量、血缘、映射和规则版本                 | 代替业务负责人填报               |
| 系统管理   | 管理组织、账号、角色、安全、运行和配置发布                   | 默认业务事实写权限               |

政策计划、授权和执行由独立后端领域负责，但前端不再增加一套孤立顶级菜单：相关任务进入“我的工作”，相关业务在对应库存、主体和政策账户上下文内完成，政策全景由授权用户从“市场监测”或全局搜索进入。

### 5.2 全局框架

全局框架保留：

- 当前组织或责任空间；
- 当前区域；
- 当前作物年度或营销年度；
- 全局搜索；
- 任务；
- 通知；
- 帮助；
- 个人账号与安全入口。

页面采用：

- 稳定的一级导航；
- 业务工作区内的上下文导航；
- 可折叠的筛选与业务上下文区域；
- 对象列表、对象全景档案和任务工作台三种主要页面形态；
- 轻量、克制、以浅色工作区为主的企业视觉体系；
- 深色导航只承担层级和定位，不成为大面积内容背景；
- 颜色只用于状态、风险和操作强调，不用于装饰。

地区、年度、品种和业务事项等上下文选择器由服务端根据当前权限、有效主数据、报送义务和已存在版本生成：

- 地区只显示当前角色可见或可负责的有效范围；
- 年度来自已生成业务期间、有效任务或已发布版本，新增年度由报送计划生成，不在前端写死；
- 品种来自受控产品和品种主数据；
- 业务事项只显示当前对象具备能力且当前角色可执行的事项；
- 没有可用项时说明缺少权限、配置、任务还是数据，不显示伪造默认值。

### 5.3 地理业务范围

首期业务覆盖：

- 齐齐哈尔市：梅里斯达斡尔族区、八个县和一个县级市；
- 黑河市：全域；
- 呼伦贝尔市：扎兰屯市、阿荣旗、莫力达瓦达斡尔族自治旗和鄂伦春自治旗。

正式区县、乡镇和行政村清单不得写死在页面或程序中，必须来自带版本和生效期的权威行政区划主数据。

系统统计村级数据时只使用行政村，不把自然村作为行政汇总节点。

三个业务区域的乡镇和行政村数量由指定日期的正式行政区划版本自动计算并展示：

- 统计日期；
- 区划版本；
- 有效乡镇数量；
- 有效行政村数量；
- 停用、合并、拆分和更名记录；
- 数据来源和审核状态。

没有权威版本和统计日期时，系统不得展示一个无法复核的固定总数。

### 5.4 责任岗位与有效任职

人员不直接拥有永久业务数据。

责任写入权限来自：

```text
人员
→ 有效任职关系
→ 责任岗位
→ 责任范围
→ 当期报送义务
```

责任范围至少包含：

- 组织；
- 业务域；
- 报送事项；
- 地理范围；
- 行政或统计区划版本；
- 监测对象范围；
- 品种或产品；
- 生效开始和结束时间。

约束：

1. 同一责任坐标在任一时刻只能有一个唯一可写负责人。
2. 协办人、查看人、审核人和管理员不得获得该报送义务的业务值写入权限。
3. 任职有效期统一使用“包含开始时间、不包含结束时间”的半开区间。
4. 父子区域、对象集合、全部产品与部分产品的相交必须使用版本化范围展开规则在服务端检测。
5. 责任配置保存前和当期报送义务生成时必须各执行一次重叠检查。
6. 缺少唯一可写负责人的计划不得生效，也不得生成可填写的报送义务。
7. 每期报送义务在生成时固定唯一写入人；后续只能通过正式责任转移改变。
8. 查看、审核、发布和管理范围与填报范围分别授权。
9. 管理员不能因为拥有系统管理权限而自动获得业务写权限。
10. 账号停用不删除人员、任职和历史责任。

### 5.5 正式责任转移

系统不提供非正式代填。

请假、离职或组织调整时只允许正式责任转移：

- 转移申请和审批；
- 原岗位和新岗位；
- 原负责人和新负责人；
- 生效时间；
- 原因；
- 受影响任务；
- 未完成任务处理方式；
- 原草稿处理方式；
- 审批人和审计事件。

规则：

- 责任转移原子生效，无重叠和空档。
- 历史已完成任务保留原负责人。
- 未来任务由新负责人承担。
- 未完成任务只能逐项选择转交、正式关闭、正式免报或正式取消，不能继续保留给已失去写权限的原负责人。
- 原草稿作者永不被改写。
- 新负责人继续填报时形成带来源关系的新修订。
- 逾期责任归截止时刻有效负责人。
- 后续补填执行人单独记录。
- 已提交但尚未审核的单据仍保留原提交人；转移后如被退回，由新负责人基于被退回版本创建新修订。
- 转移申请人不得批准自己的转移。
- 转移与提交并发时，以服务端事务提交顺序和责任版本号判定；过期责任版本的提交必须拒绝。
- 岗位任职、受影响义务、原草稿冻结与来源关系以及审计事件必须在同一事务中完成；任一步失败时整体回滚。
- 不允许以早于审批完成时间的时间点追溯生效；确需纠正历史配置时必须走独立审计更正流程，不改变既有履责事实。

### 5.6 报送计划、业务日历与报送义务

报送计划版本化定义：

- 业务域和报送事项；
- 适用组织、区域、对象和产品；
- 日报、周报、月报、年度或事件频率；
- 业务期间计算规则；
- 开放时间；
- 截止时间；
- 宽限时间；
- 催办和升级时间；
- 时区；
- 节假日、调休、停报和延期规则；
- 表单版本；
- 质量规则版本；
- 审核和发布链；
- 各审核节点的生成条件、办理时限和最终审核截止规则；
- 生效期。

系统根据计划生成每期报送义务。

合格提交触发版本化审核任务。每个审核任务固定审核节点、负责人范围、生成时间、截止时间、被审核修订和状态；审核完成率按审核任务计算，不用含糊的“应该完成”临时判断。

每期义务固定：

- 计划版本；
- 业务期间；
- 实际开放和截止时间；
- 义务生成时负责人；
- 当前唯一写入人；
- 责任转移历史；
- 截止时刻最终归责人；
- 责任坐标；
- 适用对象；
- 单据引用；
- 服务器接收时间；
- 当前处理状态；
- 时效结果。

“截止时刻最终归责人”在义务生成时为空，只能在到达截止时刻后根据有效责任历史冻结。截止前正式转移会改变当前唯一写入人及预计归责人，但不改写义务生成时负责人；正式免报或取消仍保存最后责任历史，但从应报基数中按规则排除。

任何事后延期、豁免或取消都必须形成审批记录，不能覆盖原始截止判断。

每期义务必须同时保存：

- 原始截止时间；
- 当前有效截止时间；
- 延期批准时间；
- 宽限结束时间；
- 首次合格提交时间；
- 原始时效结果；
- 生效时效结果；
- 例外处置结果。

时间规则：

- 默认业务时区为中国标准时间，计划可显式指定其他合法时区。
- 提交请求在完成身份、责任和完整请求体检查并持久保存幂等键与请求摘要后，由服务器固定接收时间；业务阻断校验随后执行。
- 只有校验通过的提交请求才产生“首次合格提交时间”，其取值使用已经固定的服务器接收时间；校验失败不产生合格提交时间，重新提交产生新的服务器接收时间。
- 截止前接收、截止后完成校验但最终通过的请求，按固定接收时间判断；系统必须保留校验开始、完成和结果时间。
- 原始时效结果始终按原始截止时间判定。
- 生效时效结果按截止前已批准的当前有效截止时间判定。
- 全系统统一采用“首次合格提交时间小于或等于截止时间”为按时，接口、数据库约束、快照和报告不得使用严格小于的另一套规则。
- 宽限期内提交仍判定为逾期提交，但在宽限结束前暂不触发上级升级。
- 截止前批准的延期可以改变当前有效截止时间，但保留原始截止时间和审批轨迹。
- 截止后批准的延期不能重写原始时效结果，只能形成正式豁免或例外处置。
- 当期义务始终引用生成时固定的业务日历和计划版本；后续日历修改不改变历史义务。

### 5.7 独立状态模型

不得使用一个状态字段同时表达全部含义。以下状态分别保存并通过允许组合矩阵约束。

#### 报送义务状态

```text
未开放
→ 进行中
→ 已到期
→ 已关闭
```

并列终态：

```text
正式免报
正式取消
```

#### 时效结果

```text
待判定
按时提交
截止未提交
逾期后补交
不适用
```

按时提交以首次合格提交的固定服务器接收时间小于或等于适用截止时间为准。

“截止未提交”保存截止时刻事实；后续补交后当前状态可以变为“逾期后补交”，但原截止事实不得删除。

#### 单据修订状态

```text
草稿
→ 已提交
```

并列状态：

```text
已撤回
已作废
已被新修订替代
```

已提交修订不可原位改写。审核退回是审核结果，不改变已提交修订内容；整改必须创建引用被退回修订的新草稿。撤回、作废和替代不删除任何修订内容。

#### 审核流程状态

```text
未开始
→ 审核中
→ 审核通过
```

审核中可以包含版本化节点：

```text
待审核
→ 初级复核
→ 最终复核
```

并列结果：

```text
退回整改
审核拒绝
审核取消
```

#### 发布版本状态

```text
候选准备中
→ 候选就绪
→ 已发布
→ 已被替代
```

并列状态：

```text
候选作废
已撤回
```

发布审核使用独立审核流程；“审核中”不是发布版本状态。候选作废用于未发布候选，已撤回只用于曾经发布的版本。发布撤回只增加状态事件和说明，不删除已发布内容。

#### 质量评估状态

```text
未评估
通过
警告
阻断
```

每个质量评估实例必须明确目标是单据与原始主张，还是规范事实与发布候选，并固定规则包版本。提交审核和发布审核使用不同审核实例及权限链，不能把前者通过当作后者自动通过。

按时提交后被审核退回，不改变其首次时效结果，但必须单独记录质量和审核结果。

规则校验属于质量评估过程，不作为单据修订状态。

全局允许组合矩阵固定最低约束：

| 业务条件           | 报送义务           | 时效结果             | 当前单据修订           | 审核流程                                     | 发布版本                     | 质量评估           |
| ------------------ | ------------------ | -------------------- | ---------------------- | -------------------------------------------- | ---------------------------- | ------------------ |
| 尚未开放           | 未开放             | 待判定               | 无                     | 未开始                                       | 无                           | 未评估             |
| 已开放但无合格提交 | 进行中             | 待判定               | 无或草稿               | 未开始                                       | 无                           | 未评估、警告或阻断 |
| 截止仍无合格提交   | 已到期             | 截止未提交           | 无或草稿               | 未开始                                       | 无                           | 未评估、警告或阻断 |
| 已形成合格提交     | 进行中或已到期     | 按时提交或逾期后补交 | 已提交                 | 未开始、审核中、审核通过、退回整改或审核拒绝 | 无、候选准备中或候选就绪     | 通过或已批准警告   |
| 正式免报或取消     | 正式免报或正式取消 | 不适用               | 无、已撤回或已作废     | 未开始或审核取消                             | 无或候选作废                 | 未评估             |
| 已完成并关闭       | 已关闭             | 按时提交或逾期后补交 | 已提交或已被新修订替代 | 审核通过、审核拒绝或审核取消                 | 无、已发布、已被替代或已撤回 | 通过或已批准警告   |

矩阵按被引用的具体单据修订、审核实例和发布版本判断，不把一个义务下的多次修订压成一个状态。退回后可以同时存在“旧修订已提交且审核结果为退回整改”和“新修订为草稿”，两者通过替代关系关联。

矩阵之外的组合默认拒绝。报送计划可以引用更严格的版本化组合矩阵，但不能放宽以下全局不变量：

- 阻断质量不能审核通过或进入候选就绪；
- 已撤回、已作废的单据修订不能启动新的审核或发布；
- 审核未通过不能进入候选就绪或已发布；
- 已撤回或已被替代的发布版本不能成为当前正式指针；
- 正式免报、正式取消和截止未提交不能产生事实发布版本；
- 退回整改保留原已提交修订，整改只能创建新草稿和新审核实例。

### 5.8 对象全景档案

对象全景档案用于聚合展示：

- 主体或样本基本资料；
- 设施和地点；
- 角色、能力和有效关系；
- 相关报送义务和单据；
- 业务事实；
- 质量问题；
- 审核与发布；
- 证据和历史时间轴。

对象全景档案不是：

- 万能对象表；
- 万能业务单据；
- 单一写入事务；
- 跨业务事实复制中心。

判断是否分开单据的规则：

- 生命周期不同，分开；
- 报送频率不同，分开；
- 负责人不同，分开；
- 审核链不同，分开；
- 更正和撤销规则不同，分开；
- 只要业务目标和对象相同，仍在同一全景工作区组合展示。

### 5.9 类型化业务事实

后台事实分为：

1. 观察：面积、单产、成本、价格、质量、意愿等。
2. 状态快照：某时点库存、设备状态、样本状态等。
3. 业务事件：销售、收购、加工、运输、盘点调整等。
4. 估计事实：按抽样或模型产生的区域估计。
5. 批准调整：有原因、证据和审批的显式调整。

事实采用：

```text
最小事实信封
＋事实类型专属载荷
＋可重复的对象、地点、产品和来源关系
```

最小事实信封只保存所有事实都成立的字段：

- 稳定事实标识；
- 事实类型；
- 业务发生时间或有效期间；
- 系统记录时间；
- 来源单据和修订；
- 报送批次；
- 幂等键；
- 质量状态；
- 审核和发布引用；
- 业务责任组织；
- 来源报送义务和唯一填报负责人；
- 记录创建人；
- 证据引用；
- 当前修订和替代关系。

专属载荷按事实类型定义：

- 数量观察保存数值、单位、精度、观测对象和观测方法；
- 库存快照保存库存批次、地点、时点、数量、所有者、保管方和库存性质；
- 交易保存交易行、买卖双方、价格条件、交付和结算状态；
- 运输保存起点、终点、运输分段、装卸和边界穿越；
- 加工保存投入批次、产出批次、副产品、损耗和转换基准；
- 样本状态保存监测方案、成员状态、生效期和原因；
- 批准调整保存目标事实、调整量、原因、证据和审批。

被观察主体、交易参与方、库存所有者等业务参与关系由事实类型专属载荷或可重复关系表达，不与业务责任组织、填报负责人或记录创建人混为一个“责任主体”。

对象、地点、产品、质量和来源根据事实类型以结构化关系重复出现，不为不适用的事实制造空字段或伪造“不适用值”。

不得用字符串能力列表替代正式角色、能力和有效关系。

### 5.10 原始主张与规范事实

业务参与方上报的是原始主张，不直接等于最终规范事实。

统一链路：

```text
单据修订
→ 不可变原始报送主张
→ 主张结构、责任、口径和证据质量门禁
→ 提交审核
→ 候选匹配
→ 冲突与重复处置
→ 类型明确的规范事件或规范快照
→ 规范事实完整性、守恒和采用质量门禁
→ 发布审核
→ 产情、市场和供需投影
```

规则：

- 原始主张不可覆盖或删除。
- 多方主张通过交易、批次、运输、时间、数量、地点和来源标识匹配。
- 自动匹配必须保存算法版本、置信度和匹配依据。
- 低置信度或冲突主张进入人工处置，不能直接进入正式指标。
- 规范事实必须列出全部来源主张。
- 匹配只解决“多方是否在描述同一事实”的身份问题，不因主体、数量或时间相似就压缩整条业务链。
- 农户销售主张与企业采购主张可能是同一交易或交付事实的两方证据；规范后只形成一份相应交易或交付事实。
- 装运、保管交接、统计边界穿越、到货和收货是可先后发生的不同物理事件，必须分别保存并通过运输任务、批次和时间顺序关联，不能合并成一个万能移动事件。
- 区域流入或流出只由唯一统计边界穿越事实产生；交易、装运、到货和收货只能作为来源或校验证据，不能各自形成可相加流量。
- 规范事实被修订时生成新版本，并保留原规范事实和来源主张。

### 5.11 产情监测

产情监测业务边界为：

```text
监测方案与样本治理
农业经营主体、家庭、受访人和地块
作物季与田间观测
面积、测产、单产和产量
成本、补贴、保险和赔付
农户库存快照和库存变动
农户销售事件
下一年度种植意愿
区域估计与正式发布
```

#### 三类来源

```text
行政村台账
农技站专业观察
农户样本
```

三类来源并列比较或按版本化采用规则选择，不直接相加。

每个正式指标必须配置一种采用策略：

- 行政台账直接采用；
- 农技站专业估计；
- 农户样本加权估计；
- 以某一来源为基准、其他来源用于校准；
- 多源联合估计。

采用策略必须保存：

- 适用指标；
- 基准来源；
- 冲突阈值；
- 校准方法；
- 权重或模型；
- 覆盖要求；
- 不确定性计算；
- 审批和版本。

没有正式采用策略时，三类来源只能并列展示，不能生成正式区域总量。

行政村必须是正式行政村，不使用自然村作为行政汇总节点。

村委会、乡镇政府和县级政府属于组织、上报、复核或发布责任，不等同于行政区域本身。

#### 地点作用

面积和产量按耕地实际所在地归属。

农户身份、居住地、耕地所在地和库存存放地分别保存。

#### 面积、单产和产量

- 区分播种面积、收获面积、弃收或未收获面积以及灾害影响指标。
- 正式集合关系为“播种面积 = 收获面积 + 弃收或未收获面积”。
- 灾害影响面积、成灾面积和绝收面积属于灾害事件及严重程度，不与收获面积并列相加。
- 绝收面积可以进入弃收或未收获面积构成；受灾但仍收获的面积仍属于收获面积。
- 产量公式优先使用收获面积和正式单产。
- 保留斤/亩等原始值，统一换算为吨/公顷。
- 只保存一份权威数值，其他单位由系统派生。
- 行政台账可以按有效行政层级汇总。
- 当同一指标、期间和产品的全部有效下级行政单元均已纳入且口径一致时，父级行政台账总量等于下级总量之和；覆盖不完整时必须展示缺失下级和覆盖率，不得伪装成完整父级总量。
- 农户样本必须经过抽样估计，不能要求样本合计等于行政村总量。

#### 成本、补贴和保险

不含保险的生产资源成本项目至少包括：

- 地租；
- 种子；
- 农药；
- 化肥；
- 灌溉；
- 人工；
- 机耕。

保险作为成本工作区中的独立保障项目展示，保费纳入生产经济成本，但不混入上述生产资源项目。

后台分别保存：

- 经济成本发生；
- 实际现金支出；
- 适用面积和分摊依据；
- 保险保单；
- 总保费；
- 财政补助；
- 农户自缴；
- 保险赔付；
- 种植补贴应收；
- 种植补贴实收。

派生指标分别命名：

- 生产经济成本；
- 农户现金投入；
- 政策支持；
- 保险赔付；
- 扣除现金补贴后的种植现金负担；
- 扣除保险赔付后的净资金负担。

种植补贴和保险赔付不得直接命名为负成本。

正式公式：

```text
生产经济成本
= 不含保险的各项生产资源经济成本
+ 保险总保费

农户现金投入
= 农户实际支付的生产资源支出（不含保险）
+ 农户自缴保费

政策支持
= 已确认种植补贴
+ 政府承担的保险保费补助
+ 其他经批准支持

实际收到的现金政策支持
= 农户实际收到的种植补贴
+ 农户实际收到的其他现金支持

扣除现金补贴后的种植现金负担
= 农户现金投入
− 实际收到的现金政策支持

扣除保险赔付后的净资金负担
= 扣除现金补贴后的种植现金负担
− 农户实际收到的保险赔付
```

政府承担的保险保费补助不从“农户现金投入”或“种植现金负担”再次扣除，因为该补助没有进入农户实际现金支出。保险赔付属于风险补偿，不与“政策支持”合并，只有在计算净资金负担时单独扣除。

灾害经济损失作为独立分析事实，不与保险赔付或生产成本相互冲销。

每项成本、补助和保险事实必须保存适用面积和分摊依据；不得使用同一个面积分母计算全部每亩成本。

后台优先保存总金额、适用面积和原始计量单位；每亩金额和每公顷金额由系统按同一权威值派生，采用“一公顷等于十五亩”的法定换算关系。两个单位不得同时作为可编辑竞争值。

#### 农户库存、销售和种植意愿

- 库存保存时点快照。
- 收获入库、购入、受赠、转入、转出、代存开始、代存结束、自用、饲用、种用、销售、损耗和批准调整保存为类型明确的事件或期间流量。
- 代存只改变物理地点或保管方，不自动改变所有权；购入、受赠和销售是否改变所有权由对应业务事件和生效时点决定。
- 累计销售量由有效销售事件汇总。
- 上期已发布的农户库存采用值生成下期农户库存期初候选，是否进入正式供需期初仍执行产品账户结转规则。
- 新盘点形成差异，不生成第二个竞争期初值。
- 种植意愿引用当前正式面积。
- 意愿保存目标作物年度、调查轮次、预计面积和原因。
- 各品种意向面积受可用耕地总量约束。

#### 全年产情能力

若模块正式命名为“产情监测”，应纳入：

- 生育进程；
- 墒情；
- 灾情；
- 病虫害；
- 测产轮次；
- 收获进度。

若业务不采集上述内容，应将模块定义收窄为年度种植生产调查，不能使用超出能力的名称。

### 5.12 市场监测

市场监测业务边界为：

```text
经营主体、设施、关系与业务能力
产品、质量规格、粮食批次和检验
报价
交易
库存与盘点
加工转换和直接消费
运输任务、运输分段和边界穿越
政策库存账户与代储关系
市场样本估计和正式发布
```

#### 主体、设施和关系

分别建模：

- 经营主体；
- 设施和物理地点；
- 所有关系；
- 经营关系；
- 租赁关系；
- 保管关系；
- 政策代储关系；
- 业务角色；
- 业务能力；
- 生效期。

四个概念不得混用：

- 业务角色：主体在业务网络中的身份，例如贸易商、加工企业、承储企业；
- 业务能力：可以执行的业务动作，例如收购、仓储、加工、检验、运输；
- 能力模板：用于快速配置一组能力、字段和默认规则；
- 设施类型：仓库、工厂、生产线、批发市场、铁路站点等物理资源分类。

角色和能力必须按有效期保存。选择模板只产生可审核的配置，不永久锁死主体，也不得据此复制一份主体档案。

贸易商、加工企业、承储企业和粮食消费主体是业务角色；收购、报价、交易、仓储、加工、检验、销售、运输和直接消费是业务能力。

销售是业务能力，不是与企业并列的主体类型。

政策储备是库存政策账户或代储关系，不是企业类型。

铁路和公路是运输节点或运输方式，不是企业角色。

#### 品种、质量和价格条件

玉米业务至少支持：

- 受控品种主数据或“待确认临时品种”；
- 水分；
- 容重；
- 毒素；
- 杂质；
- 不完善粒；
- 霉变；
- 包粮或散粮；
- 到厂、出库或车板等交付条件。

大豆业务至少支持：

- 受控品种主数据或“待确认临时品种”；
- 普通大豆或蛋白大豆等业务分类；
- 蛋白；
- 水分；
- 杂质；
- 不完善粒；
- 筛粮或塔粮等加工状态；
- 包粮或散粮；
- 到厂、出库或车板等交付条件。

稻谷和大米业务至少支持：

- 受控品种主数据或“待确认临时品种”；
- 稻谷类别；
- 水分；
- 杂质；
- 不完善粒；
- 出糙率；
- 出米率；
- 包装和交付条件。

任何价格必须绑定适用质量、产品形态、包装、交付条件、方向和有效时间。

计价条件还必须明确币种、价格单位、含税或不含税、发票口径、结算币种、折价扣量规则及适用版本。页面展示“元/吨”等价格时必须能够反查上述完整条件，不能把不同税价、质量或交付口径直接比较。

临时品种必须保存原始填报名称、填报人和时间。主数据管理员确认映射后生成新映射版本，不改写原始名称；未确认品种可以保存，但能否进入正式区域指标由质量规则决定。

质量概念必须分开：

- 报价质量要求：报价适用于什么质量区间；
- 合同约定质量：买卖双方约定的交付条件；
- 批次质量身份：粮食批次当前已确认的质量属性；
- 检验结果：某样品按某标准和方法得到的测量事实；
- 结算质量：最终用于折价、扣量或付款的确认结果。

质量指标作为上述业务事实的结构化关联，不形成一套脱离报价、合同、批次、检验或结算语境的重复台账。

#### 报价

报价至少包含：

- 买入或卖出方向；
- 产品和具体品种；
- 质量要求；
- 包装方式；
- 交付条件；
- 报价；
- 有效开始和结束时间；
- 报价主体和设施。

报价不等于成交，不进入交易数量。

#### 交易

交易头至少包含：

- 买卖双方；
- 合同或成交标识；
- 业务状态；
- 签订时间；
- 结算主体；
- 责任组织。

交易行至少包含：

- 产品、具体品种和产品形态；
- 合同数量、单位和允许偏差；
- 合同价格或计价规则；
- 合同约定质量；
- 包装和交付条件；
- 计划交付地点和期间。

实际履约通过批次分配关联：

```text
交易行
→ 一个或多个交付批次
→ 装运、到货和验收
→ 实际交付数量
→ 结算质量与扣价扣量
→ 结算金额
```

批次分配必须保存分配数量、所有权转移时点、风险转移时点、实际交付时点和结算状态。一个批次或批次份额分配到多条交易行时，总分配量不得超过可分配量。

粮食发生部分装运、分仓、分配或加工时，原批次必须拆分为带父批次血缘的原子批次份额。各有效子份额数量之和等于拆分前数量，原父份额停止作为可用库存；合批时生成引用全部来源份额的新批次，不覆盖来源历史。

签订合同不等于实物已经流动。

取消、退货、更正和未交付必须有明确状态和事件。

#### 质量检验

质量检验至少包含：

- 样品；
- 粮食批次；
- 检验标准；
- 检验方法；
- 检验时间；
- 检验机构；
- 指标结果。

原重、净重、标准水分折算量必须区分。

#### 库存

库存是一份物理状态和多个正交维度：

```text
物理地点
＋库位
＋产品和批次
＋时点
＋数量
＋所有者
＋保管方
＋库存性质
＋粮源属性
＋物料状态
```

企业库存、政策库存、原料库存和成品库存不能作为同一级数字直接相加。

库存盘点、库存流水和账面余额之间的差异必须形成有原因的处置记录。

库存统一确认采用三本相互勾稽但不可混算的账：

1. 物理库存账：某时点实际位于哪个库位或在途位置的粮食；
2. 所有权库存账：某时点归哪个所有者所有的粮食；
3. 库存属性账：原料、在制、成品、商品、政策性质等正交属性。

“企业库存”只表示查询范围，不是可以与商品粮、原料、成品或政策库存相加的新库存类别。

区域物理库存采用以下唯一确认规则：

- 已售未发仍只计在实际存放地点的物理库存，所有权变化另记；
- 装货完成并由承运方接管后，批次份额从起点库位变为在途物理位置，不再计入起点静态库存；
- 在途粮食按可证明的实际位置归属区域；越过版本化统计区域边界时生成唯一边界穿越事实和区域流入、流出；
- 到货并完成收货确认后才进入终点物理库存；
- 截止时点位置不明确时标记为“在途待定位”，不分配给起点或终点静态库存，单列数量并按重要性门禁阻断或暂估正式区域总量；
- 农户、企业、代储和政策库存通过规范批次、物理地点和时点合并去重；
- 同一原子批次份额同一时点只能有一个有效物理位置，可以有一个所有者和一个或多个有明确份额的权益方；
- 盘点事实、流水推算余额和调查估计分别保存，只有通过批准的采用规则才能生成正式库存指标。

“保管接管边界”只改变库位或在途状态，“统计区域边界”只按地理边界穿越事件改变区域流量，“所有权转移边界”只改变所有权账。三者分别配置和取证，不得使用一个未定义的“确认边界”代替。

正式指标必须配置库存合并矩阵，明确每一种主体、设施、库存属性、所有权和物料状态是“纳入、排除、作为构成展示或仅用于校验”。矩阵版本必须随指标发布固定。

#### 加工与直接消费

加工记录：

- 生产线；
- 报告期间或班次；
- 原料投入批次；
- 实际投料量；
- 主要产品；
- 副产品；
- 实际产出量；
- 转换率版本；
- 技术损耗；
- 开机时间、停机时间和原因。

加工必须进行数量和质量基准勾稽：

```text
标准基准投入量
= 主要产品标准基准产出量
+ 副产品标准基准产出量
+ 经批准损耗
+ 在制品变化
```

原始重量、标准水分重量和干物质重量分别保存。转换规则必须声明采用哪一种基准、水分标准、杂质扣除、允许误差和舍入方式。

“原粮当量”只作为版本化派生指标，不得伪装成真实物理库存或真实物流事实。

原粮供需只在第一次不可逆投料或直接原粮消费时计入使用。

成品后续销售和消费不能再次折回原粮账户重复计算。

#### 物流

```text
运输任务
→ 一个或多个运输分段
→ 装货和卸货
→ 起点和终点
→ 统计边界穿越
```

同一运输由发货方、收货方、铁路站点或公路节点分别报送时，作为多方证据匹配，只生成一个规范移动事实。

铁路、公路是运输方式分解，不能与父级流入或流出重复相加。

#### 政策业务

政策业务不是普通库存上的一个文本标签，至少建模：

- 政策计划和法规依据；
- 政策账户；
- 收储、投放、拍卖和轮换授权；
- 委托方、承储方、库点和保管责任；
- 品种、数量、质量、有效期间和区域范围；
- 收购、入库、移库、轮换、投放、拍卖、出库和结清事件；
- 可见范围、敏感级别和审批链。

政策授权、政策执行事件、物理库存和所有权库存相互关联，但各自保持独立生命周期。没有有效授权不得把普通库存改标为政策库存；政策账户内部性质变化不得自动生成区域流入、流出、供给或使用。

### 5.13 抽样与区域估计

任何样本数据进入正式区域估计前必须定义：

- 监测方案；
- 目标总体；
- 样本框；
- 分层；
- 抽取概率；
- 基础权重；
- 无回答调整；
- 校准权重；
- 样本退出、拒访、失联和替换规则；
- 估计方法版本；
- 标准误；
- 置信区间；
- 设计效应；
- 覆盖率；
- 质量等级。

市场监测必须明确某类企业是全量台账、重点样本还是概率样本。

未完成抽样设计的数据只能表达样本范围，不得直接发布为区域总量。

抽样框覆盖率、样本响应率、履责应报对象覆盖率和有效数据覆盖率使用不同指标编码、分子和分母；普通页面不得用一个没有限定词的“覆盖率”混指。

### 5.14 产品与转换

产品模型至少区分：

- 作物；
- 原粮商品；
- 受控具体品种；
- 待确认临时品种；
- 产品形态；
- 质量规格；
- 包装和交付条件；
- 计量基准；
- 原粮当量派生口径；
- 转换率版本；
- 加工转换关系。

示例：

```text
水稻作物 → 稻谷 → 大米、米糠、稻壳
大豆作物 → 原豆 → 豆粕、豆油、蛋白产品
玉米作物 → 原粮玉米 → 淀粉、酒精及其他产品
```

不同产品形态的物理吨数不得直接相加。

产品转换必须保存投入、主产品、副产品、损耗、在制品变化和质量基准。转换率不得只有一个百分比；必须同时声明适用产品、品种、工艺、地区、期间、水分或干物质基准、允许误差、证据和批准版本。

同一加工事实同时产生：

- 上游产品账户的一次加工使用；
- 下游产品账户的一次生产供给；
- 可独立核验的副产品和损耗；
- 指向同一加工运行的跨账户血缘。

下游产品销售不得再次折回上游原粮账户计作第二次使用。

### 5.15 供需平衡

供需只读取：

- 已发布的指标版本；
- 质量门禁通过；
- 单位和产品口径明确；
- 业务坐标一致；
- 来源和版本可追溯；
- 已完成去重；
- 在计算截止时点内有效的规范指标。

每个产品账户必须先发布一份可执行账户规范，固定：

- 账户产品和允许的产品形态；
- 统计区域边界；
- 营销年度和截止时点；
- 计量单位、标准水分或干物质基准；
- 供给角色、使用角色和仅展示不相加角色；
- 每类规范事实到角色的映射规则；
- 构成项与父项关系；
- 跨产品转换关系；
- 库存合并矩阵；
- 缺失、暂估、冲突和覆盖率门禁；
- 舍入、容差和勾稽规则；
- 规则版本、审批和生效期。

在同一个产品账户和统计期间内，一个规范事实最多进入一个可加总供需角色。铁路、公路、政策性质、商业性质、企业类型、质量等级等构成维度只能分解该角色，不能再次作为与父项并列的加项。

同一物理链路跨产品账户时，通过加工转换成对记账：

```text
上游产品账户：加工使用
↕ 同一加工运行与转换版本
下游产品账户：生产供给
```

区域总账户：

```text
总供给
= 该产品账户规范中全部互斥可加总供给角色之和

期间使用与外流
= 该产品账户规范中全部互斥可加总使用与外流角色之和

调整前账面推算期末库存
= 总供给 − 期间使用与外流

采用后账面期末库存
= 调整前账面推算期末库存
+ 经审核发布的净库存调整

库存平衡差额
= 调查汇总期末库存 − 采用后账面期末库存
```

常用供给角色库包括期初库存、本地产量、国际进口和区域外流入；常用使用角色库包括直接食用、直接饲用、种用、加工投料、不经加工的直接工业使用、数量损耗、国际出口和区域外流出。每个产品账户只启用物理含义明确且相互排斥的角色；未启用角色不生成空字段。“不经加工的直接工业使用”与“加工投料”必须由物理事件排他，不能把加工用途再作为并列加项。

净库存调整只能来自类型明确的批准调整事实，必须显示原因、证据、审批和对下一期期初的影响，不得为追求账面闭合而自动生成。

页面可使用“总需求”业务名称，但数据字典必须明确其含义为期间总使用与外流，不是市场询价或意向需求。

#### 玉米

- 产量以收获面积和正式单产为主要依据。
- 播种面积用于过程监测和校验。
- 春玉米是玉米产量构成，不与总产量重复相加。
- 铁路和公路流量是流入或流出的运输方式构成。
- 期初商业库存和期初政策库存是期初总库存的所有权构成，不再与期初总库存重复相加。
- 政策国产玉米和政策进口玉米是政策库存的粮源构成。
- 使用角色固定为直接食用、直接饲用、种用、加工投料、数量损耗、国际出口和区域外流出。
- 淀粉、酒精、食品等用途是“加工投料”的目的构成；不得再设置一个与加工投料并列且口径重叠的“深加工需求”或“工业需求”加项。
- 养殖企业和饲料企业的原粮直接投料必须按最终物理用途映射，不能同时进入饲用和加工投料。

#### 大豆

- 原豆、豆粕、豆油和蛋白产品分别建账户。
- 压榨投料进入原豆使用。
- 豆粕、豆油生产进入下游产品供给。
- 原豆账户使用角色固定为直接食用、压榨投料、非压榨蛋白加工投料、种用、数量损耗、国际出口和区域外流出。
- “蛋白消费”只有在物理对象被确认是原豆直接投入蛋白加工时，才进入“非压榨蛋白加工投料”；若指豆粕或蛋白产品消费，则进入相应下游产品账户。
- 同一批原豆不能同时进入压榨投料和非压榨蛋白加工投料。
- 非转基因进口是进口属性或子项，不与进口总量重复相加。
- 政策性库存和商业库存是期末总库存的所有权构成，不与期末总库存重复相加。
- 储备收购和储备投放在政策库存账户展示；除非同时穿越统计边界，不增加区域物理账户的总供给或总使用。

#### 稻谷与大米

- 建立稻谷和大米两个关联账户。
- 稻谷加工投料按批准出米率生成大米生产。
- 出米率按地区、年度、品种或工艺版本化。
- 加工出率差不得再次计为一般损耗。
- 对外主表可采用双账户或明确标注的稻谷当量。
- 稻谷与大米物理吨数不得直接相加。
- 稻谷账户使用角色固定为直接食用、直接饲用、种用、碾米加工投料、其他加工投料、数量损耗、国际出口和区域外流出。
- 大米账户供给中的本地生产只来自可追溯的稻谷碾米加工运行；使用角色固定为食用、其他加工投料、饲用、数量损耗、国际出口和区域外流出。
- “食用”必须声明统计的是稻谷直接使用、大米终端食用，还是稻谷当量展示；三者不得混成一个未标注数字。
- 出糙率、出米率、米糠、稻壳和碎米共同参与加工平衡，不能只根据一个出米率生成无法勾稽的产出。

#### 政策库存

当区域总库存已包含政策库存时：

- 政策收购；
- 托市收购；
- 储备投放；
- 托市拍卖；
- 政策轮换；

属于库存所有权或政策性质内部转移，不增加区域总供给或总使用。

只有同时穿越统计区域边界时，跨界部分才产生流入或流出事实。

政策账户独立展示期初、收购、投放、拍卖、轮换、跨区调拨、损耗和期末，并与物理库存账户勾稽。政策账户回答所有权和政策执行问题，区域物理账户回答粮食实际在哪里以及如何流动，两者不能合并成一张可相加宽表。

#### 期末结转与下一期期初

每个产品账户的账户规范必须固定期末采用和结转规则：

- 调整前账面推算期末、采用后账面期末和调查汇总期末分别保存；
- 默认下一期正式期初只能引用上一期已发布的“采用后账面期末库存”；
- 调查汇总期末只有满足覆盖率、质量、去重和勾稽门禁后，才可通过批准库存调整进入采用后账面期末；
- 调查差额未获批准时只作为库存平衡差额和风险展示，不能直接覆盖账面期末；
- 下一期期初固定引用的上一期供需结果发布版本和期末指标标识，不允许再次手工填写竞争期初值；
- 上一期发生正式重述时，所有下游期初和供需版本标记为待重算，按血缘级联重算、复核和重新发布，旧版本保持不变；
- 首个基准年度期初必须来自经盘点、迁移对账或其他正式批准的基准库存版本，并保存来源、截止时点、覆盖范围和审批。

#### 缺失值

正式值必须区分：

- 有值；
- 真实为零；
- 缺失；
- 不适用；
- 暂估；
- 被质量规则阻断。

关键输入缺失时阻断正式发布，禁止自动补零。

#### 初步态势与正式结果

实时监控、预警和经营调度可以读取当期初步数据，但必须：

- 与正式指标使用相同业务定义、单位和规范事实标识；
- 显著标记“初步”“暂估”“未完成审核”及数据截止时点；
- 不覆盖或冒充正式发布结果；
- 可追溯到尚未完成的报送、质量和审核环节；
- 在正式版本发布后切换到对应正式结果，并保留前后差异。

### 5.16 正式发布、重述和血缘

发布分为四种独立实体和生命周期：

1. 事实发布版本：固定通过门禁的规范事实集合；
2. 指标发布版本：固定指标定义、聚合规则及其计算结果；
3. 供需结果发布版本：固定账户规范、输入指标和供需计算结果；
4. 报告发布版本：固定报告内容、引用版本集合和文件。

四类版本各自使用 5.7 唯一发布状态字典：候选准备中、候选就绪、已发布、候选作废、已撤回和已被替代。审核状态只保存在关联审核实例中，不复制到发布版本。不得用一个发布记录同时代表四层；下游版本可以引用上游版本，但不能反向改写上游内容。

每一种正式发布使用共通发布信封，固定：

- 稳定发布标识和发布类型；
- 业务坐标；
- 截止时点；
- 上游版本引用清单；
- 内容清单和内容哈希；
- 质量与审核记录引用；
- 前序、替代和撤回关系；
- 发布人和发布时间。

各层专属内容分别固定：

- 事实发布：规范事实清单、来源主张清单、去重规则和质量规则版本；
- 指标发布：事实发布版本清单、指标与单位、聚合或估计、产品转换和质量规则版本；
- 供需结果发布：指标发布版本清单、账户规范、库存合并矩阵、公式、参数和计算代码构件版本；
- 报告发布：事实、指标和供需发布版本清单、报告定义、模板、生成规则、生成代码构件和文件哈希。

所有引用清单采用稳定顺序规范序列化并计算集合哈希；不适用于某一层的字段不得伪造空版本或“不适用版本”。

已发布版本不可覆盖。

修订必须：

- 发起重述；
- 说明原因；
- 选择受影响事实；
- 生成新输入版本；
- 重新审核；
- 重新计算；
- 发布新版本；
- 指向被替代版本。

任一供需结果单元格都必须能够追溯：

```text
结果
→ 计算运行
→ 公式和转换版本
→ 正式指标
→ 规范事实
→ 原始单据和证据
→ 填报、质量、审核和发布记录
```

版本标识必须在各层保持类型明确，页面不得把事实版、指标版、供需版和报告版都简写成一个无法辨认的“数据版本”。

### 5.17 履责快照

日报、周报和月报履责统计必须使用不可变快照。

每个快照先固定“应报基数集合”：

```text
应报基数集合
= 截止时点前已到期且有效的报送义务
− 截止时点前已批准并生效的正式免报
− 截止时点前已批准并生效的正式取消
```

免报和取消数量必须作为独立构成展示，不能从报告中消失。截止时点后批准的免报、取消或延期不得反向改写既有快照，只能形成新的当前视图或更正版本。

核心指标使用以下唯一公式：

```text
原始按时率
= 首次合格提交时间不晚于原始截止时间的应报义务数
÷ 应报基数义务数

有效按时率
= 首次合格提交时间不晚于生效截止时间的应报义务数
÷ 应报基数义务数

应报对象覆盖率
= 已形成至少一份合格提交的应报对象坐标数
÷ 应报基数中的应报对象坐标数

有效数据覆盖率
= 截止时点前通过阻断性质量门禁且被接受的必报指标单元数
÷ 截止时点前应填的必报指标单元数

审核完成率
= 截止时点前已完成的到期审核任务数
÷ 截止时间小于或等于快照截止时点的有效审核任务数
```

“首次合格提交”必须至少通过结构完整性和提交门禁，空表、无效文件和仅保存草稿不计入。正式批准的不适用指标从有效数据覆盖率分母排除并单列数量；分母为零时展示“不适用”，不得显示百分之零。

正式取消的审核任务从审核完成率分母排除并单列；退回整改完成了当前审核任务，但新修订提交后生成新的审核任务。审核通过率和审核完成率是不同指标，不得互相替代。

时间统一使用服务器保存的带时区时间，业务日历明确采用时区。比率保留完整精度计算，展示统一四舍五入到一位小数；导出同时保存分子、分母和未舍入值。

每个报送计划必须声明履责报告归属规则，默认按义务原始截止时间所在的业务日历日、业务周或业务月归属。实际提交时间、逾期补填和事后延期不移动原报告归属。跨月业务周作为完整周保留起止日期，不拆成两个竞争周报；月报按固定归属规则纳入义务，并可引用跨月周报但不复制其统计事实。

快照固定：

- 统计期间；
- 数据截止时点；
- 报送计划和业务日历版本；
- 应报义务清单；
- 截止时刻最终归责人；
- 按时提交；
- 逾期补填；
- 仍未填报；
- 正式免报；
- 正式取消；
- 单据状态；
- 质量状态；
- 首次提交人、首次合格提交时间和最后有效提交时间；
- 单据修订、表单版本、填报对象数和有效指标数；
- 逾期原因、补填执行人和补填时间；
- 来源义务标识；
- 内容哈希。

后续补填不得改写原快照。

快照只追加不替换，并保存前序快照标识、规范序列化内容哈希和生成运行标识。

新版本显示：

```text
原截止状态：逾期仍未填
当前状态：已于某时补填
原责任人：某人员
补填执行人：某人员
```

### 5.18 报表中心

报表中心分为：

#### 履责报告

回答：

- 谁应报；
- 谁按时报；
- 谁逾期后补填；
- 谁仍未填；
- 哪些任务被退回；
- 哪些任务存在质量阻断；
- 哪些责任发生转移。

至少展示：

- 原始按时率；
- 有效按时率；
- 应报对象覆盖率；
- 有效数据覆盖率；
- 审核完成率。

第一版不生成一个不可解释的综合评分。

#### 业务分析报告

用户选择：

- 产情、市场、政策、供需或组合业务；
- 地区；
- 品种和产品；
- 业务期间；
- 数据截止时点；
- 正式引用版本清单或经授权的初步数据层；
- 指标和分析维度；
- 报告模板。

系统生成：

- 正式文档报告；
- 固定版式报告；
- 数据明细表；
- 图表附件。

#### 报告生命周期

```text
报告定义
→ 周期计划或临时任务
→ 数据版本锁定
→ 报告生成运行
→ 事实反查
→ 人工复核
→ 审批发布
→ 不可变报告文件
→ 更正、撤回或替代
```

正式报告必须只引用已发布的事实、指标或供需结果版本。

需要及时性的未审核数据只能生成明确标记的“初步报告”，不得与正式报告混用，也不得使用正式报告发布状态。

报告至少固定：

- 报告定义和模板版本；
- 业务期间；
- 数据截止时间；
- 事实发布版本清单；
- 指标发布版本清单；
- 供需结果发布版本清单；
- 其他获准引用版本清单；
- 引用版本集合哈希；
- 指标定义版本；
- 生成规则版本；
- 生成时间；
- 生成人；
- 审核人；
- 发布人；
- 文件哈希；
- 被替代报告版本。

报告下载记录是独立审计事件，保存下载人、授权上下文、时间、用途、文件版本和结果，不写入报告不可变内容，也不因新增下载记录改变报告文件哈希。

### 5.19 自动中文报告

自动报告采用：

```text
结构化正式事实
→ 确定性规则生成数字和结论骨架
→ 受约束的语言润色
→ 数字、主体和来源自动反查
→ 人工复核
→ 正式发布
```

规则：

- 语言模型不得重新计算正式数值。
- 不得编造原因、主体、事件或结论。
- 因果解释必须来自数据证据或人工填写的正式分析意见。
- 模型不可用时，确定性模板仍能生成可用报告。
- 人员、库存和政策敏感数据不得发送到未经批准的外部服务。
- “去人工智能痕迹”定义为正式、自然、无模板腔、无开发术语、可核验的中文，不定义为规避检测或隐瞒生成过程。

### 5.20 权限与职责分离

权限由以下共同决定：

```text
角色能力
＋责任范围
＋对象和字段敏感性
＋数据状态
＋动作
＋时间和环境条件
```

服务器对每次操作重新鉴权。

权限采用默认拒绝。决策顺序为：

1. 法律、隐私、职责分离、数据状态或显式禁止命中时拒绝；
2. 责任坐标和有效任职不匹配时拒绝写入；
3. 其余角色允许项可以合并；
4. 没有明确允许时拒绝。

显式禁止和职责分离约束优先于角色允许。管理员、审核人、发布人和填报人的能力不能因为角色叠加而绕过相互制约。

必须覆盖：

- 菜单；
- 搜索建议；
- 列表和详情；
- 数量统计；
- 消息通知；
- 新增和修改；
- 提交；
- 审核；
- 发布；
- 批量导入；
- 导出；
- 报告生成；
- 报告下载；
- 历史版本；
- 责任转移；
- 直接输入地址访问详情；
- 附件和原始证据；
- 审计记录；
- 临时下载链接；
- 消息推送；
- 查询缓存和离线缓存；
- 后台任务及其产物。

职责分离：

- 填报人不能最终发布自己的数据。
- 审核人不能直接修改填报值。
- 公式管理员不能自行批准公式并发布受影响结果。
- 系统管理员不能默认修改业务事实。
- 例外批准必须保存原因、证据和审批人。

所有导出和报告必须再次执行数据范围和字段脱敏。

权限撤销必须形成可验证的失效链：

- 未开始的后台任务取消；
- 已运行任务在读取下一批数据、写入结果和发布产物前重新鉴权；
- 已完成产物在每次下载时重新鉴权；
- 临时下载链接和相关缓存立即失效；
- 浏览器中已加载的敏感数据在收到失效通知或下一次鉴权失败时清除；
- 已打开页面不得凭旧令牌继续提交、审核、发布或导出。

服务端在撤权事务提交后的下一次请求立即应用新权限。缓存、临时链接、消息订阅和浏览器清理的候选传播上限为 60 秒；运行中后台任务至少每处理一批数据且最长每 60 秒重新鉴权，并在任何文件或正式结果可见前再次鉴权。最终时限必须经安全容量测试签字。

接口故障时可以保留上一份成功加载的数据，仅限当前授权仍有效；授权状态无法确认或已撤销时必须隐藏敏感内容。

审计事件采用只追加记录，至少包含：

- 人员、账号、有效岗位和组织；
- 动作、目标类型和稳定目标标识；
- 业务坐标和数据范围；
- 请求时间、服务器完成时间和统一关联标识；
- 变更前后版本或内容哈希；
- 权限决策、职责分离结果和授权依据；
- 原因、证据和审批引用；
- 成功、拒绝、冲突或失败结果；
- 导出、下载和外发的文件版本、用途和接收范围。

审计时间使用统一校时的服务器时间。审计记录、业务记录和文件证据必须能够互相反查；审计访问本身也要审计。留存期、归档层级、法律冻结和合规销毁按数据分类配置，任何业务页面不得直接物理删除正式发布、正式报告或仍在留存期内的审计证据。

### 5.21 隐私

农户使用稳定匿名标识。

姓名、电话、证件和精确住址仅在有明确业务必要时保存，并与统计事实分离。

普通列表、分析、日志、履责报告和对外报告不得显示不必要的个人信息。

履责报告属于人员管理数据，必须限制查看、导出和传播。

### 5.22 全中文与技术信息隔离

普通业务界面和正式文件必须：

- 菜单、按钮、状态、提示和错误均使用中文；
- 不显示内部枚举、数据库字段、接口路径和程序堆栈；
- 不显示开发占位、组件试验或技术兼容页面；
- 日期、数字和单位使用统一中文格式；
- 内部技术标识只在授权运维诊断层查看；
- 运维诊断层仍以中文解释问题，并附内部关联标识供排障。

系统内部代码、协议和技术标识可以使用技术语言，但不得泄漏到普通业务界面。

### 5.23 配置驱动边界

允许配置：

- 字段中文名称、顺序和分组；
- 适用地区、产品、角色和报送频率；
- 单位、枚举、必填和数值范围；
- 表单版本和生效期；
- 报送计划和业务日历；
- 报告模板；
- 质量规则参数；
- 指标展示方式。

必须由后端权威实现，不能交给前端任意配置：

- 正式权限；
- 行政和区域汇总；
- 库存结转；
- 物流去重；
- 供需公式；
- 产品转换；
- 发布门禁；
- 责任唯一性；
- 任意可执行脚本。

### 5.24 技术架构

前端采用：

- React；
- Refine Core；
- Ant Design；
- ProComponents；
- TypeScript；
- Vite；
- 内部企业组件适配层。

业务页面只依赖内部企业组件和领域用例，不大面积直接绑定第三方组件私有配置。

后端优先采用模块化单体，领域边界包括：

- 身份与组织；
- 责任与报送；
- 主数据和监测方案；
- 产情监测；
- 市场监测；
- 质量与审核发布；
- 规范指标；
- 供需计算；
- 报告中心；
- 审计与运行保障。

只有出现可证明的独立扩容、独立发布、独立团队所有权或吞吐瓶颈时，才拆分服务。

写模型采用类型明确的业务表。

宽表、看板和报告使用独立查询模型、物化结果或缓存，不作为业务写入来源。

领域契约不依赖 Refine、Ant Design 或具体数据库表名，降低技术栈锁定风险。

### 5.25 批量导入与责任约束

批量导入只是录入方式，不是绕过责任、质量或审核的后门。

每个导入批次固定：

- 文件哈希、文件名、模板版本和来源；
- 上传人、上传组织和上传时间；
- 解析规则和代码版本；
- 每行原始内容、行号和行哈希；
- 目标报送计划、期间和业务坐标；
- 解析、匹配、校验、确认和提交结果。

每一行都必须校验当期报送义务、唯一可写负责人、责任坐标、产品、地区和有效期。

上传人、责任负责人和最终提交人分别记录：

- 管理员或辅助人员可以上传并隔离文件；
- 只有该义务的唯一可写负责人可以确认行映射、形成业务草稿并最终提交；
- 审核人和管理员不能通过导入代替责任人生成已提交事实；
- 责任转移后，未提交导入行随任务正式转移，原负责人失去确认和提交权；
- 重复文件、重复行和重复业务事实分别检测，不以覆盖旧数据处理；
- 部分错误可以形成隔离结果，但发布到业务草稿或正式事实的动作必须按约定原子边界执行并可回滚。

### 5.26 并发、幂等和后台任务

- 草稿、单据、责任配置、规则和正式候选携带强版本标识。
- 更新必须携带期望版本；不匹配时返回冲突和可比较差异，不静默覆盖。
- 创建、提交、审核、发布、转移、计算、导入确认和报告生成必须携带幂等键。
- 幂等键作用域至少包含租户或组织、操作者、动作和业务坐标。
- 服务端同时保存请求摘要；同一键和同一摘要返回原结果，同一键和不同摘要返回明确冲突。
- 幂等结果和唯一约束持久化，客户端超时重试不能重复创建任务、版本、事实或文件。
- 普通状态变更命令的幂等记录至少保留 90 天，且不得短于客户端重试、消息重投和灾难恢复窗口中的最长者；未决任务不得清理。正式发布和正式报告的幂等记录随对应正式版本同期限保留。
- 计算或报告运行自然唯一键由运行类型、业务坐标、数据截止时点、输入版本集合哈希、账户或报告定义版本、公式或模板版本、代码构件摘要和重述意图共同组成。
- 同一运行自然唯一键只允许一个有效运行；重复请求返回既有运行标识。输入、定义、代码或重述意图不同属于合法新运行，不得误判为重复。
- 后台任务使用持久租约和心跳，租约过期才能由其他执行器接管。
- 重试采用有限次数、退避和随机抖动；超过上限进入死信或人工处置队列，不无限重试。
- 业务写入、审计事件和后续任务通知通过同一事务的发件箱记录提交，防止数据成功但消息丢失。
- 批量操作先形成不可变批次；解析、校验和发布失败不得产生部分正式数据。
- 正式发布指针使用“期望前序版本＋输入集合哈希”的条件更新；条件不一致时候选作废并重新计算。
- 并发重述不得形成分叉的正式版本链。
- 权限变化按 5.20 的规则使会话、缓存、任务和产物失效。

### 5.27 异常、不可变性与恢复

- 接口失败不得显示空白页面。
- 保留当前筛选和对象；只有当前授权仍有效时才保留已成功加载的数据。
- 明确区分无任务、无数据、无正式版本、无权限和服务失败。
- 数据刷新失败继续展示上一版正式结果。
- 计算失败不改变当前正式发布指针。
- 发布失败不产生半发布状态。
- 报告失败不产生半成品正式文件。
- 每个请求、导入、计算、发布和报告运行保存关联标识。
- 正式发布内容只能追加，业务操作不得更新或删除。
- 撤回只增加撤回事件和当前指针变化，原发布内容、原因和证据继续保留。
- 正式内容采用确定性规范序列化并计算内容哈希，默认使用 SHA-256 或经安全批准的后继算法。
- 每个哈希同时保存规范序列化方案及版本、哈希算法标识、字符编码和清单排序规则版本，保证多年后仍可复验。
- 版本链不得出现循环或未经批准的分叉；同一业务坐标同一层级只能有一个当前正式指针。
- 计算代码构件、规则包和报告模板保存可验证摘要，不能只保存可变版本名称。

候选生产恢复目标：

| 数据类别                                 |                               恢复点目标 |              恢复时间目标 |
| ---------------------------------------- | ---------------------------------------: | ------------------------: |
| 已确认成功的正式发布与正式报告           | 零数据丢失；成功响应前完成同步持久化副本 | 核心只读服务不超过 4 小时 |
| 草稿、报送义务和业务运行事实             |                           不超过 15 分钟 | 核心填报服务不超过 4 小时 |
| 已被正式版本引用的附件、证据、审计和配置 |       零数据丢失，不允许出现孤立正式引用 |             不超过 8 小时 |
| 尚未发布的附件、证据、配置和任务队列     |                           不超过 15 分钟 |             不超过 8 小时 |

上述目标是准入候选值，必须经过基础设施容量和成本评审后签字；未签字时不得宣称生产灾备已经达标。

恢复保障至少包括：

- 传输和静态加密；
- 独立故障域或异地备份；
- 数据库、附件、原始证据、报告文件、配置、审计、队列和发布构件的整体恢复；
- 每月抽样恢复验证；
- 每季度完整灾难恢复演练；
- 恢复后校验内容哈希、版本链、当前指针、报送任务、执行租约和发件箱；
- 演练保存实际恢复点、实际恢复时间、差异、责任人和整改闭环。

### 5.28 新旧系统与数据库

新系统采用独立前端仓库和版本化接口契约。

旧系统保持可运行，直到：

1. 新领域词汇和指标字典冻结；
2. 新数据库模型完成；
3. 旧数据映射规则签字；
4. 迁移回放和对账通过；
5. 新旧并行验收通过；
6. 回退演练通过；
7. 正式切换稳定期结束。

旧数据分为：

- 可无损映射到新口径；
- 需要转换或拆分；
- 只能保留为历史只读；
- 无法确认语义、不得进入正式新口径。

旧数据库在完成归档、哈希、备份、映射和验收前不得删除。

## 六、测试决策

### 6.1 最高层验收接缝

最高层只保留一条完整业务链：

```text
配置责任岗位
→ 生成当期报送义务
→ 唯一负责人填报
→ 时效与质量判定
→ 审核并形成事实发布版本
→ 生成指标发布版本
→ 供需自动计算并发布结果版本
→ 日报、周报或月报锁定同一引用版本集合
```

该链必须在真实权限、真实状态、真实版本和真实持久化环境中通过。

页面、接口和模块测试都服务于这条主链。

### 6.2 测试原则

- 优先测试可观察业务行为，不测试内部实现细节。
- 每个失败场景必须证明系统拒绝错误结果，而不是只证明正常路径成功。
- 权限测试必须从服务端验证，不能只检查按钮隐藏。
- 供需测试必须覆盖缺失、冲突、重复、负值、极值、转换和修订。
- 并发测试必须证明不会静默覆盖或重复发布。
- 报告测试必须证明数字和版本与正式数据一致。
- 恢复测试必须证明失败不破坏上一版正式结果。
- 全中文测试扫描所有普通业务页面、错误和导出文件。

每个验收用例必须采用统一证据格式：

```text
前置条件与固定数据版本
→ 操作人、权限、责任坐标和动作
→ 接口结果与用户可见结果
→ 领域状态和持久化结果
→ 审计、通知和后台任务结果
→ 旧版本不可变性与禁止副作用
→ 响应时间、资源和关联标识
```

用例不能只写“测试通过”。必须给出明确预期，例如拒绝请求的业务原因、正式指针保持不变、审计事件恰好一条、同一幂等请求返回同一结果标识以及未生成重复任务。

最高层验收链的关键断言：

1. 同一责任坐标存在两个可写负责人时，计划不能生效且不生成可填写义务。
2. 唯一负责人提交后，其他人员、审核人和管理员均不能改写业务值。
3. 截止后补填只更新当前状态，不改写截止快照和原始时效结果。
4. 质量阻断或审核未通过时，不产生事实发布版本。
5. 供需运行只引用固定的指标发布版本集合，重复运行得到相同内容哈希。
6. 报告引用固定的事实、指标和供需版本集合；后续重述不改变旧报告。
7. 任一步失败时，上一正式版本和当前正式指针保持可用。

### 6.3 责任与履责测试

至少覆盖：

1. 同一责任坐标尝试配置两个主要负责人。
2. 父区域与子区域责任范围重叠。
3. 责任在截止前一分钟正式转移。
4. 原负责人已有草稿后发生责任转移。
5. 逾期任务转给新负责人补填。
6. 原负责人尝试继续修改已转移数据。
7. 管理员尝试代替填报人修改业务值。
8. 设备时间错误但服务器时间正确。
9. 节假日、调休和正式延期。
10. 按时提交后被审核退回。
11. 提交空表试图获得按时状态。
12. 后续补填不改写历史履责快照。
13. 请求恰好在截止时刻由服务器完整接收。
14. 截止前接收但截止后完成阻断校验并最终通过。
15. 截止前转移后冻结义务生成负责人、当前写入人和截止归责人。
16. 尝试形成状态组合矩阵禁止的状态。
17. 审核任务跨报告截止时点时的审核完成率。

### 6.4 产情测试

至少覆盖：

1. 农户居住地、耕地所在地和库存地不同。
2. 行政村和自然村名称相同但标识不同。
3. 行政村台账、农技站和农户样本给出不同结果。
4. 播种面积、收获面积和灾损面积勾稽。
5. 亩和公顷转换。
6. 不同成本项使用不同适用面积。
7. 保险总保费、财政补助、农户自缴和赔付。
8. 销售事件生成累计销售。
9. 上期期末滚转与新期盘点差异。
10. 种植意向面积超过可用耕地。
11. 样本失联、拒访和替换。
12. 区域估计展示覆盖率和置信区间。
13. 不含保险的资源成本、总保费、现金补贴和保险赔付分别计算。

### 6.5 市场测试

至少覆盖：

1. 同一法人拥有、租赁和代管不同设施。
2. 米厂同时具有贸易、仓储、加工和销售能力。
3. 政策粮存放在商业企业仓库。
4. 报价没有成交。
5. 合同签订但尚未交付。
6. 交易取消、退货和结算扣价。
7. 一份交易多行、一行多批次和一个批次分配到多行。
8. 报价质量、合同质量、检验质量和结算质量不同。
9. 同一批粮多次质检。
10. 原重、净重、标准水分重量和干物质重量。
11. 已售未发发生所有权变化但物理库存地点不变。
12. 库存盘点与账面余额差异。
13. 企业库存查询范围不得与原料、成品或政策属性重复相加。
14. 加工投入生成主要产品、副产品、损耗和在制品变化。
15. 同一运输由多方报送。
16. 一票运输包含铁路和公路两个分段。
17. 区域内部交易不形成区域流入或流出。
18. 年末在途粮食不重复进入两地库存。
19. 临时品种确认映射不改写原始填报名称。
20. 无有效政策授权时尝试将普通库存标记为政策库存。
21. 一百吨父批次拆成六十吨在途和四十吨留库，数量守恒且位置唯一。
22. 保管接管、所有权转移和统计区域穿越发生在不同时间。

### 6.6 供需测试

至少覆盖：

1. 玉米正常闭合账户。
2. 播种面积与收获面积不同。
3. 父指标和铁路、公路构成重复输入。
4. 大豆压榨与蛋白消费口径冲突。
5. 原豆到豆粕、豆油的转换。
6. 稻谷到大米的转换。
7. 稻谷和大米物理吨数尝试混算。
8. 政策库存内部转移。
9. 国际进口与区域流入重复。
10. 缺失值尝试补零。
11. 调查汇总库存覆盖不足。
12. 库存平衡差额超阈值。
13. 公式版本升级和历史重述。
14. 并发发布同一坐标。
15. 计算失败仍保留上一版正式结果。
16. 同一规范事实尝试映射到同一账户两个可加总角色。
17. 玉米加工投料与深加工用途构成重复。
18. 原豆压榨和非压榨蛋白加工使用同一批次。
19. 稻谷直接食用、大米食用和稻谷当量混用。
20. 事实版、指标版、供需版和报告版独立发布与替代。
21. 初步态势与正式结果同时存在且标识清楚。
22. 调查汇总期末未通过门禁时不能覆盖采用后账面期末。
23. 调查差额获批后形成显式库存调整并滚转到下一期期初。
24. 上期供需版本重述触发下游期初待重算，但不改写旧版本。
25. 首个基准年度期初能够追溯盘点或迁移批准版本。

### 6.7 报告测试

至少覆盖：

1. 日报、周报和月报使用配置业务日历。
2. 报告锁定固定数据截止时点。
3. 报告引用固定的事实、指标和供需发布版本清单及其集合哈希。
4. 后续补填不改变历史报告。
5. 报告修订生成替代版本。
6. 数字、主体和来源自动反查。
7. 语言润色服务不可用时使用确定性模板。
8. 自动文字不得生成不存在的原因。
9. 内部和对外报告使用不同审批链。
10. 报告导出和下载权限。
11. 报告内容全中文。
12. 大批量报告并发、限流、重试和恢复。

### 6.8 权限与安全测试

至少覆盖：

1. 查看未授权区域。
2. 修改未授权对象。
3. 利用父区域权限越权修改子区域专属事项。
4. 通过搜索建议推断敏感对象。
5. 通过统计数字推断未授权数据。
6. 通过导出或报告绕过字段权限。
7. 审核人修改原始值。
8. 填报人发布自己的数据。
9. 系统管理员修改业务事实。
10. 权限撤销后的旧会话和缓存。
11. 后台任务在权限变化后继续执行。
12. 敏感农户和政策库存数据泄漏。
13. 通过直接地址、附件、证据或临时下载链接绕过权限。
14. 已运行导出在发布文件前被撤销权限。
15. 管理员上传文件后尝试代替唯一负责人确认并提交。
16. 同一用户叠加填报、审核和发布角色后违反职责分离。
17. 撤权后服务端下一请求立即拒绝，缓存、链接和运行任务在约定时限内失效。

### 6.9 性能和稳定性测试

正式容量值必须根据批准的业务量模型签字。签字前采用以下不降低的候选基线：

- 容量场景取“预计生产峰值的三倍”和“500 个并发已登录会话、100 个并发写操作、20 个并行长任务”两者中的较高值；
- 普通列表、详情和搜索在容量场景下第 95 百分位不超过 2 秒，第 99 百分位不超过 5 秒；
- 不含文件上传和长任务的创建、保存、提交、审核等核心命令第 95 百分位不超过 2 秒；
- 报告、导入、导出和供需批量计算在 2 秒内受理并返回任务标识，不占用同步请求等待；
- 批准的基准年度全量供需计算第 95 百分位在 10 分钟内完成；
- 批准的基准日报、周报和月报批次第 95 百分位在 10 分钟内完成；
- 容量场景下服务端非业务拒绝错误率低于 0.1%，无静默覆盖、重复发布或丢失已确认写入；
- 月度核心服务可用性候选目标为 99.9%，计划维护窗口另行约定；
- 正式发布和正式报告达到 5.27 的零数据丢失目标，核心服务达到不超过 4 小时的恢复时间目标。

性能和稳定性场景至少包括：

- 代表性宽表服务端分页、排序、筛选和汇总；
- 大批量导入、重复文件、坏行隔离和原子失败；
- 多人并发填写不同单据；
- 同一单据版本冲突和幂等重试；
- 供需批量计算和同坐标并发发布；
- 日报、周报和月报批量生成；
- 大文件导出、流式下载和下载中途撤权；
- 消息和催办高峰；
- 缓存失效和旧权限清理；
- 数据库连接耗尽；
- 后台任务租约接管、重试风暴和死信处置；
- 备份恢复和灾难恢复。

测试报告必须记录数据规模、并发模型、软硬件配置、持续时间、响应时间分布、吞吐、错误分类、资源峰值和关联标识，禁止只报告平均响应时间。

### 6.10 正式准入门槛

以下门槛全部有证据通过后，才能称为大型企业生产级架构：

1. 领域词汇唯一。
2. 责任范围无重叠且历史可追责。
3. 报送计划和业务日历可重现。
4. 每个页面字段映射到唯一事实。
5. 产情和市场抽样设计可执行。
6. 交易、库存、加工和物流完成去重闭环。
7. 产品转换和供需账户正确。
8. 关键缺失值不补零。
9. 审核、发布和重述不可覆盖。
10. 任一正式值可完整追溯。
11. 权限、职责分离和隐私测试全部通过。
12. 并发、幂等、失败恢复和备份恢复通过。
13. 报告与正式版本一致。
14. 普通业务页面和正式文件全中文。
15. 管理者、填报人、审核人、发布人和分析人员完成可用性验收。

准入证据分别由以下责任方签字，任何一方不得代替其他专业责任：

| 证据范围                       | 最终签字责任         |
| ------------------------------ | -------------------- |
| 业务流程、角色和可用性         | 业务负责人           |
| 指标、抽样、转换和供需公式     | 统计与供需口径负责人 |
| 主数据、血缘、质量和旧数据映射 | 数据治理负责人       |
| 权限、职责分离、隐私和审计     | 安全与合规负责人     |
| 容量、监控、备份和灾难恢复     | 运维负责人           |
| 功能、并发、失败和回归测试     | 质量负责人           |
| 正式版本、报告文件和留存       | 档案与记录负责人     |

准入包必须包含测试数据版本、自动化结果、人工验收记录、缺陷清单、未关闭风险、性能报告、恢复演练报告和各责任方签字。任何阻断项未关闭时，只能标记为试运行或初步版本。

## 七、范围外

本规格不包括：

- 立即修改本地 MySQL；
- 立即连接或写入云 PostgreSQL；
- 立即删除旧数据库或旧前端；
- 在设计阶段确定全部物理表名和迁移编号；
- 将当前模拟前端直接接入生产；
- 第一版全面微服务化；
- 第一版建设完整数据湖；
- 第一版实现未经评估的乡村离线同步；
- 使用未经批准的外部语言模型处理敏感业务数据；
- 用综合分数替代客观履责指标；
- 允许管理员或其他填报人非正式代填；
- 将样本数据无估计规则地冒充区域总量；
- 将价格、质量、成本和意愿直接相加进粮食供需数量。

## 八、补充说明

### 8.1 待业务签字事项

以下事项没有通用答案，必须在对应正式指标发布前签字：

1. 大豆“蛋白消费”的物理对象和账户归属。
2. 区域总库存是否完整包含政策库存。
3. 商业库存是否包含加工企业原料库存和其他企业库存。

5. 稻米对外主表采用双账户还是稻谷当量。
6. 玉米加工、工业、饲用和食用分类的互斥规则。
7. 各品种和区域的营销年度起止日期。
8. 农户和企业样本的外推方法及最低覆盖要求。
9. 调查汇总库存通过批准调整进入采用后账面期末库存的质量门槛。
10. 库存平衡差额的预警、阻断和批准调整阈值。
11. 周报业务周规则。
12. 法定节假日、调休、宽限期和延期规则。
13. 内部报告与对外报告的审批链。
14. 自动语言润色允许使用的部署方式和数据边界。

未签字事项不阻止无歧义的技术骨架建设，但相关正式指标和报告不得发布。

### 8.2 方案成熟度结论

本规格采用的不是“页面最多”或“技术最复杂”的方案，而是：

- 用户工作入口统一；
- 相同业务集中展示；
- 不同事实保持真实边界；
- 同一事实只有一个权威写入口；
- 责任、时效、流程、质量和发布相互独立；
- 业务事实、指标、供需结果和报告逐层生成；
- 必要位置追加留痕，但不引入全系统事件重放复杂度；
- 当前优先模块化单体，保留未来按证据拆分的能力。

这是当前业务规模、现有系统条件和长期演进目标下的最佳适配候选。

它不能通过口头承诺被称为“绝对完美”，只能在本规格的正式准入门槛全部通过后，被称为大型企业生产级粮食商情平台。
