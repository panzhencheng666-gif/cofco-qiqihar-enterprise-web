## 一、总决策

采用“新系统独立建设、旧系统只读迁移、按垂直业务链分阶段验收”的方案。

| 范围     | 决策                                                                   |
| -------- | ---------------------------------------------------------------------- |
| 新前端   | 继续使用 `/Users/federal/Desktop/cofco-qiqihar-enterprise-web`         |
| 新后端   | 新建 `/Users/federal/Desktop/cofco-qiqihar-enterprise-backend`         |
| 新数据库 | 新建独立 MySQL 8.4 LTS 数据库，不复用旧库表结构                        |
| 旧前端   | 保持可运行，作为业务对照和回退来源                                     |
| 旧后端   | 冻结为只读迁移源；只借鉴行为模式，不直接承载新版领域                   |
| 旧 MySQL | 完成备份、哈希、映射、对账、并行和回退前不得删除                       |
| 分支     | 每个新仓库只保留 `main` 和一个当前集成分支，不为每个小任务建立长期分支 |
| 发布     | 不推送、不部署、不切换生产，直到准入包签字                             |

### 为什么不在旧后端继续重构

旧后端当前分支有 387 项工作区变化，其中约 266 项删除和 108 项未跟踪；同时仍基于 Java 8、Spring Boot 1.5、Tomcat 7 和 WAR 部署。它包含可借鉴的鉴权、审核发布、审计和事务发件箱模式，但直接继续写入会同时承担：

1. 用户未提交包迁移现场被覆盖的风险；
2. 旧业务语义渗入新领域模型的风险；
3. 老技术升级和业务重构相互阻塞的风险；
4. 新旧数据库迁移无法回退的风险。

因此采用“复用经验和验收行为，不复制脏代码和旧表”的方式。

## 二、技术基线

### 2.1 前端

沿用当前已锁定并通过基础门禁的版本：

- React 19.2.8；
- Refine Core 5.0.12；
- Ant Design 5.29.3；
- ProComponents 2.8.10；
- TypeScript 5.9.3；
- Vite 8.1.5；
- Vitest 4.1.10；
- Playwright 1.62.0；
- Node.js 24.18.x。

业务页面只依赖内部企业组件适配层和领域用例。第三方组件升级通过适配层吸收，不把页面锁死到组件私有配置。

### 2.2 后端

首个技术尖峰固定验证以下组合：

- Java 25 长期支持版；
- Spring Boot 4.1.0；
- Spring Modulith 2.1.0；
- Maven Wrapper及分发校验；
- Spring MVC、Spring Security、Spring Session JDBC、Spring JDBC；
- MySQL 8.4 LTS；
- Flyway 13.0.0；
- Testcontainers MySQL；
- OpenAPI 3.1 契约；
- Micrometer、结构化日志和健康检查。

技术锁文件必须同时记录 JDK 发行版、Maven Wrapper 版本与分发 SHA-256、Spring Modulith BOM、MySQL 容器精确补丁版与镜像摘要、所有直接依赖和构建插件版本。禁止使用可漂移的 `latest` 或只写 `mysql:8.4` 作为验收证据。

选择依据：

- Spring Boot 4.1.0 官方要求至少 Java 17，并明确兼容到 Java 26；
- Spring Modulith 2.1.0用于验证模块边界、模块测试、运行可观测和事务事件；
- MySQL 8.4 是稳定行为的长期支持分支；
- Flyway 13 要求 Java 21 以上，与 Java 25 基线一致。

尖峰不通过时不自行拼接版本，必须记录失败证据并选择官方兼容矩阵中的稳定组合。

官方依据：

- [Spring Boot 4.1.0 系统要求](https://docs.spring.io/spring-boot/system-requirements.html)
- [Spring Modulith 2.1.0 参考文档](https://docs.spring.io/spring-modulith/reference/index.html)
- [MySQL 8.4 长期支持发布模型](https://dev.mysql.com/doc/refman/8.4/en/mysql-releases.html)
- [Flyway 13 开源 Java 接入方式](https://documentation.red-gate.com/flyway/reference/usage/api-java)

### 2.3 架构形态

后端为一个可独立部署的模块化单体。首期不建立微服务、消息集群或分布式事务。

```text
应用入口
├── 身份与组织
├── 责任与报送
├── 主数据与监测方案
├── 产情监测
├── 市场监测
├── 质量、审核与发布
├── 规范指标
├── 供需计算
├── 报表中心
└── 审计与运行保障
```

模块之间只通过公开应用接口和领域事件协作。只有出现可证明的独立扩容、发布、团队所有权或吞吐瓶颈时才拆服务。

### 2.4 代码结构规范

代码结构不是“文件放整齐”或“通过格式化”即可验收，必须同时满足业务语义集中、依赖单向、接口精简和实现可替换。

后端规范：

- 采用模块化单体，每个业务模块具有小而稳定的公开接口和较深的内部实现；
- 模块内部按领域、应用用例和外层适配器分工，不建立只有转发作用的空服务层；
- HTTP 控制器只做协议转换，事务和业务规则由应用用例协调，领域对象维护不变量，仓储适配器只负责持久化；
- 业务模块不依赖 Web、数据库和框架内部类型；
- 模块间禁止访问 `internal` 包，禁止循环依赖和“公共工具大杂烩”；
- 统一异常、时钟、标识、版本、分页和审计接口，但不把各业务状态压成通用枚举；
- 只有真实存在两个适配器或确有替换需求时才建立接口接缝，避免无价值抽象。

前端规范：

- 编译依赖方向固定为页面与应用外壳 → 工作流/视图状态 → 领域模型；
- 工作流依赖企业网关端口，HTTP 与模拟适配器实现并依赖该端口，端口不得反向依赖适配器；
- 页面通过企业界面适配层使用 Ant Design 和 ProComponents，领域与工作流不得依赖第三方界面私有类型；
- 页面不直接调用 `fetch`、拼接接口、解释数据库错误或保存第二份业务状态；
- Refine、Ant Design 和 ProComponents 通过企业组件适配层使用，领域与工作流不依赖其私有类型；
- 跨业务共用的是交互原语和显示组件，不把产情、市场、供需的业务规则塞进通用组件；
- 同一业务单据只保留一个规范工作区和一套路由，列表、任务、搜索和审核只导航到该地址；
- 远程数据、表单草稿和界面瞬态分开管理，避免多个状态容器保存同一事实；
- 严格 TypeScript、运行时契约校验、可访问性、分页/虚拟化和按路由拆包进入门禁。

前后端分离规范：

- 新前端和新后端是两个独立 Git 仓库、两个独立构建、两个独立进程、两个独立端口和两个独立发布制品；
- 跨仓只允许通过版本化 OpenAPI/HTTP 契约协作；开发期同源代理只是联调方式，不改变部署边界；
- 前端不得包含 Java 业务实现、数据库驱动、SQL、迁移和连接配置，后端不得包含 React、Node.js 界面源码或前端构建产物；
- 两个仓库分别执行格式、静态检查、架构、测试、构建和制品校验，任何一侧失败都不能以另一侧成功替代。

每阶段生成代码结构检查报告。若现有结构不符合上述依赖，先以测试锁定行为，再做小步迁移；不得以一次性目录搬运造成大面积不可审查变化。

## 三、实施原则

1. 每一阶段只交付一条可运行的业务链，不先堆空菜单。
2. 每个页面字段必须能映射到唯一业务事实或查询投影。
3. 所有写权限在服务端执行，前端隐藏按钮不是安全措施。
4. 先写失败测试，再写最小实现，再执行完整阶段门禁。
5. 物理数据库迁移只写入新数据库；旧库访问账号只允许读取。
6. 正式事实、指标、供需和报告版本只追加不覆盖。
7. 接口契约先于前后端实现，并使用运行时校验。
8. 普通业务界面和正式文件全中文；技术诊断进入隔离运维入口。
9. 不以“平均响应时间”或“页面能打开”代替生产准入。
10. 任一阶段失败都保留上一检查点可运行状态。
11. 业务架构优先，代码结构服务于业务边界；不得为追求目录形式拆散同一业务。
12. 所有公开接口接受领域语义而不是框架类型，适配器变化不得迫使业务页面和领域规则同步重写。

## 四、阶段、依赖关系与交付物

阶段顺序是硬约束。产情和市场只能把数据送入共用事实治理链，不能各自形成一套“正式事实”；数据库工作只能在物理模型进入门禁通过后开始。

### 阶段 0A：无数据库保护、隔离、契约与技术尖峰

目标：建立不会触碰旧系统、不会误连数据库、可以重复验证的起点。

交付：

- 新规格、逻辑模型、计划和研究材料的内容哈希；
- 旧前端、旧后端、迁移、备份、被忽略文件和现有证据的只读清单与哈希；
- 本轮命令与进程的“数据库连接次数为零”证据；
- 新后端独立目录、无数据库启动配置和唯一集成分支；
- Java、Spring Boot、Spring Modulith、Maven Wrapper 和 OpenAPI 的无数据库兼容尖峰；
- JDK 发行版、Maven Wrapper 分发校验值、依赖清单、构建插件、Node.js 和容器镜像摘要的技术锁文件；
- 统一错误模型、会话安全、同源访问、管理端口隔离和日志脱敏基线；
- 新库标识、账号分权、加密备份、保留期、恢复点目标、恢复时间目标、恢复验证和回退的设计，不宣称已经演练。

本阶段禁止：

- 加载数据库驱动后尝试建立连接；
- 运行 Flyway、Testcontainers 或任何数据库集成测试；
- 创建或修改新旧数据库；
- 以开发机已有环境变量作为新系统连接配置。

退出条件：

- 旧前端、旧后端、旧数据库和旧备份均未修改；
- 新后端能以 `no-db` 配置启动，模块边界和 OpenAPI 纯契约测试通过；
- 新旧目录、环境变量前缀、数据库标识、账号和端口不存在交叉；
- 停止新进程即可回退，不影响旧系统。

### 阶段 1A：无数据库领域链、权限链与可交互前端

目标：先证明业务语义、权限语义和页面信息架构正确，再决定物理表。

依赖顺序：

```text
版本化行政区划、产品、单位和业务日历
→ 人员、账号、角色、权限与数据范围
→ 任职、责任岗位、责任范围叶子、指派与交接
→ 报送方案、期间与报送义务
→ 单据、时效、审核、审计与事务发件箱端口
→ 我的工作和标准业务单据模拟链
```

交付：

- 六套独立状态模型及其纯领域测试；
- 任职标识、无时间责任坐标、责任范围叶子展开和确定性多锁顺序；
- 权限撤销版本、安全会话、职责分离和默认拒绝规则；
- 幂等占位、规范摘要、丢失响应重放、追加式审计和事务发件箱领域端口；
- 浏览器登录、工作空间解析、责任定位、义务展示、提交和审计查看的 OpenAPI 3.1 契约；
- 前端领域模型先于传输对象，传输对象使用运行时校验；
- 仅显示“有权限且有真实能力”的导航，不建立空页面；
- 使用内存适配器完成可交互纵向演示，明确标注“未连接生产数据”。
- 生成无 SQL、无驱动、无数据库连接的物理模型 JSON 制品和人类可读摘要，完整定义首切片表、列、键、约束、索引、精度、保留和敏感分类，供门禁审批固定哈希。

退出条件：

- 同一责任坐标重叠、上下级区域重叠、全部产品与指定产品重叠均被拒绝；
- 管理员、审核人和其他填报人不能因拥有页面权限而代替负责人填报；
- 设备时间不能影响时效判定；
- 逾期补填不改写原截止快照；
- 权限或会话安全版本变化后，下一次服务端用例调用即拒绝；
- 领域模型、接口契约、页面字段和验收场景形成可追踪矩阵。
- 前后端独立仓库、构建、进程、端口、制品和跨仓契约边界通过自动检查。
- 物理模型制品通过模式与逻辑覆盖校验，但尚未获得真实签署时不得进入数据库实施。

### 物理模型进入门禁

这是数据库工作的唯一入口，不是文档勾选项。必须存在并通过模式校验的：

`docs/superpowers/verification/physical-model-entry-gate.json`

门禁至少锁定：

- 规格、逻辑模型、路线图、首个纵向切片、OpenAPI、威胁模型、恢复设计和物理模型制品的路径及 SHA-256；
- 新数据库固定标识 `qiqihar_grain_enterprise_v1`；
- 专用环境变量前缀 `QGE_DB_`；
- 旧库名、旧账号、旧地址，以及按协议、主机、端口、库名、用户、TLS 和环境规范化后通过外置密钥 HMAC-SHA-256 形成的连接指纹黑名单；
- 数据所有者、安全负责人、恢复负责人和实施负责人的真实签署记录；
- 物理模型评审、数据保留策略、恢复点目标、恢复时间目标和回退条件；
- 受控可信签署人公钥、角色、有效期和轮换记录；
- 规范化门禁清单的分离式数字签名与自动验证结果为通过。

实施人员不得代签业务、安全或恢复责任人。门禁未通过时，阶段 1A 之后的无数据库工作可以继续，任何 Flyway、JDBC、Testcontainers 和数据库端到端测试必须保持停止。

### 阶段 1B：身份、责任、报送与“我的工作”真实持久化

目标：门禁通过后，把阶段 1A 的同一条链落到全新的临时数据库与新库物理模型中。

真实纵向链：

```text
浏览器登录
→ 服务端解析权限、数据范围和会话安全版本
→ 由有效任职定位责任岗位
→ 生成并领取本人报送义务
→ 保存草稿与提交
→ 同一事务写入单据、时效、追加式审计和发件箱
→ 重启临时 MySQL 后重新读取
```

退出条件：

- 新数据库启动前防护在打开网络套接字前验证库名、账号、环境、门禁和旧库指纹；
- 集成测试只通过 `@ServiceConnection` 注入一次性 MySQL 容器，禁止复用本机连接；
- 相同幂等键并发请求只产生一个业务结果、一个审计事件和一个发件箱事件；
- 响应丢失后重试返回原结果，不重复提交；
- 权限撤销、会话吊销、交接生效和并发指派均有服务端测试；
- 浏览器端到端链在新后端和一次性 MySQL 上通过，并验证数据库重启后的读取。

详细执行计划：

`docs/superpowers/plans/2026-07-30-enterprise-foundation-first-vertical-slice.md`

### 阶段 2：共用质量、审核、规范事实与正式发布

目标：在任何产情或市场正式发布前，先建立唯一权威数据治理链。

交付：

- 原始主张、证据、匹配簇、冲突和人工处置；
- 质量规则、质量问题、审核任务和职责分离；
- 规范事实候选、批准调整、事实发布版本和当前正式指针；
- 指标定义、口径版本、事实到指标的血缘和指标发布版本；
- 替代、撤回、哈希复验和下游重算通知；
- 初步态势、审核中数据和正式结果的清晰分层。

退出条件：

- 阻断质量问题不能发布；
- 审核人只能返回原因或作出审核决定，不能直接改写填报值；
- 发布人不能发布自己提交或审核的事实；
- 同一正式坐标无分叉，旧版本不可变且哈希可复验；
- 产情和市场模块只能调用同一治理链发布正式事实。

### 阶段 3：产情监测

目标：在一个产情对象工作区内覆盖全年生产过程、成本保障、农户库存销售和种植意愿，不拆成相互孤立系统。

交付：

- 农业经营主体、农户、受访人、农技站、行政村、地块和作物季；
- 生长进程、墒情、灾害、病虫害、测产轮次和收获进度；
- 播种面积、单产、产量及村—乡镇—区县—地市的可验证汇总；
- 经济成本、现金支付、补贴应享与实收、保险缴费与赔付、灾害损失；
- 农户库存移动、销售明细和下一季种植意愿；
- 样本框、来源角色、权重、覆盖率、区域估计和不确定性；
- 通过阶段 2 共用链完成质量、审核和事实发布。

退出条件：

- 村委、农技站和农户是三类独立来源，不被直接相加；
- 行政村和自然村不能混用；
- 地块位置、居住地、库存保管地和所有权可分别表达；
- 成本项目按各自适用面积计算，补贴不直接冲减成本事实；
- 销售数量只来源于库存移动，销售详情不再保存第二份数量；
- 区域估计可追溯样本、权重、覆盖率、口径和不确定性。

### 阶段 4：市场监测

目标：以企业或设施为唯一业务对象，根据有效角色与能力呈现其适用业务，避免同一企业被拆散或重复建档。

交付：

- 企业、场所、设施、有效业务角色、能力模板和角色能力；
- 贸易、加工、养殖饲料、储备、米厂、农资经销和物流节点能力；
- 玉米、大豆、稻谷质量规格及版本；
- 报价、交易、交付、结算和退货；
- 批次、检验、物理库存、所有权份额、保管、位置、在途和盘点；
- 加工投入、产出、副产品、损耗、在制品及水分/干基换算；
- 铁路、公路运输分段和区域边界；
- 政策授权、执行和政策属性；
- 通过阶段 2 共用链完成质量、审核、去重和事实发布。

退出条件：

- 米厂等复合主体只建一次，页面按能力组合而不是按菜单复制主体；
- 报价不计为成交，同一运输多方报送只形成一个规范事实；
- 物理库存只保存一份数量，企业、商品粮、原料、成品和政策库存是互斥口径或属性投影；
- 所有权、保管、位置和在途分别生效，份额合计和待确认状态可验证；
- 批次拆分、合并、加工和损耗数量守恒；
- 农资商品、销售和库存不混入粮食供需账户。

### 阶段 5：指标、供需与态势

目标：供需结果完全由正式指标按版本化账户规则自动计算，不允许手填正式结果。

交付：

- 玉米、原豆、稻谷和大米互斥账户；
- 账户角色启用、事实映射、产品形态、跨账户转换、库存合并矩阵、边界、营销年度、截止时间和水分/干基口径；
- 调整前账面期末、采用后账面期末、调查汇总期末、差额和下一期期初滚转；
- 基准年、追溯重述、下游重算和失败回退；
- 账户勾稽、变化分析和事实—指标—账户—结果的全链血缘；
- 实时监控和区域地图读取同一指标定义与正式版本。

退出条件：

- 缺失值不补零，父指标与构成、账户之间和产品形态之间不重复相加；
- 原粮和加工品不混算，政策内部转移不增加供需总量；
- 每个账户只汇总已启用且互斥的角色；
- 重复运行内容哈希一致，失败不改变上一正式结果；
- 任一结果能追溯到公式版本、账户角色、指标版本和原始证据。

### 阶段 6：履责、日报、周报和月报

目标：同时完成责任履约管理和选择式业务报告，两类结果使用各自正确的快照。

交付：

- 单义务固定截止快照与组织/人员汇总履责快照；
- 按时、截止未提交、逾期后补交、仍未填、免报和审核完成的独立指标；
- 催办、升级和责任交接后的归属规则；
- 按业务、地区、产品、期间和正式版本集合选择生成日报、周报和月报；
- 确定性数字段落、受控中文润色、人工复核和发布；
- 文档、表格和 PDF 导出；
- 历史报告不可变、替代关系和完整来源。

退出条件：

- 周报、月报准确展示填报人、责任区域、提交时间、填报内容和补填情况；
- 补填不能改写原截止快照，汇总快照可按固定时点重现；
- 报告数字与锁定的正式版本集合完全一致；
- 语言服务不可用时仍能生成准确、无虚构内容的确定性中文报告；
- 普通用户看不到接口地址、状态码、变量名、调试标识和开发文字。

### 阶段 7：迁移、并行、容量与灾备

目标：以证据决定是否切换，不以主观观感决定上线。

交付：

- 旧数据映射、隔离区和行级血缘；
- 多轮迁移回放及数量、金额、版本和关系对账；
- 新旧系统并行结果；
- 500 会话、100 写操作和 20 长任务的候选容量验证；
- 权限、并发、幂等、恢复、大文件和故障注入测试；
- 加密备份、保留期、恢复点目标、恢复时间目标和完整灾难恢复演练；
- 回退演练、监控告警、值守手册和准入包。

退出条件：

- 规格第 6.10 节全部门槛有证据和相应责任方真实签字；
- 所有阻断缺陷关闭，容量和恢复指标达到签署目标；
- 旧系统仍可回退；
- 稳定期结束、法定保留义务满足且另行获得删除授权前不删除旧数据库。
